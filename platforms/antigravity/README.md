# `platforms/antigravity/` — Antigravity CLI adapter

Antigravity CLI (`agy`) is Google's successor to Gemini CLI for consumer tiers
(Gemini CLI stopped serving Google AI Pro/Ultra and free Code Assist users on
2026-06-18; enterprise Code Assist and paid API-key users keep it, and the
[Gemini adapter](../gemini/adapter.yaml) keeps serving them). Its plugin format is
a folder, not a `gemini-extension.json`, so it gets its own adapter.

| File | Generated by | What it is |
|------|--------------|------------|
| `plugin.json` | `scripts/build-antigravity-plugin.sh` | `{name, description}` — the schema is closed (`additionalProperties: false`), so nothing else fits |
| `mcp_config.json` | `scripts/build-antigravity-plugin.sh` | the `github` stdio server (`command`/`args`), the documented shape |
| `adapter.yaml` | hand-written | the §21 pointer file; every capability is `unknown` until a live `agy` run |
| *(no `hooks.json`)* | — | deliberately absent, see below |

Regenerate with `bash scripts/build-antigravity-plugin.sh .`; CI runs its `--check`.
`platforms/manifests.source.json`'s `antigravity` section is the overlay (description,
MCP servers); the name comes from `.claude-plugin/plugin.json`.

## Migration route: `agy plugin import gemini`

Google's migration guide documents one command that turns an installed Gemini
extension into a native plugin:

```bash
agy plugin import gemini
```

It "searches your legacy local directories, parses your extension manifests, and
converts files into native layout blocks", reporting each extension's skills, agents,
commands and `mcpServers` as converted, processed, migrated or skipped. What carries
over, per that guide:

| From Gemini CLI | To Antigravity | Note |
|---|---|---|
| `GEMINI.md` / `AGENTS.md` | unchanged | "No modifications are needed to your existing rule documents" |
| workspace skills `.gemini/skills/` | `.agents/skills/` | this repo now ships `.agents/skills/` itself (`scripts/build-agents-skills.sh`), so the tree is there before any import |
| global skills `~/.gemini/skills/` | `~/.gemini/antigravity-cli/skills/` | |
| `commands/*.toml` | converted to skills | this repo ships no commands |
| MCP servers (`settings.json` / extension manifest) | `mcp_config.json` (`~/.gemini/config/` or `.agents/`) | remote `url`/`httpUrl` become `serverUrl`; stdio keeps `command`/`args` |
| agents | "skipped (none detected)" in the documented sample | this repo's `.gemini/agents/` are Gemini-translated; whether the importer reads them is unverified |
| hooks, policies | not mentioned by the guide | unverified either way |

## Why no `hooks.json`

Google states that skills, hooks, subagents and extensions carry over "at launch"
without 1:1 parity, and one third-party source claims `agy` "loads hooks but does not
fire them". Neither was measured here: no `agy` binary was available and the CLI is
not open source, so nothing could be read from a bundle the way the Gemini rows were.
A hooks file that is loaded and never fired reads as a guard that is not one, which is
worse than an honest absence. The Gemini extension's generated hooks
([`../gemini/hooks.json`](../gemini/hooks.json)) are what an import would carry over
once firing is verified.

## What is unverified

- Whether a relative stdio `command`/`args` path in `mcp_config.json` resolves against
  the plugin directory. The docs show only absolute paths and define no placeholder
  (nothing like Gemini's `${extensionPath}`). `agy plugin import gemini` from an
  installed extension is the route known to produce absolute paths.
- Whether the import preserves `hooks/hooks.json` and `policies/*.toml`.
- Everything in `adapter.yaml`'s capability block — all `unknown` until a live run
  records otherwise in `core/capabilities/platforms.json`.
