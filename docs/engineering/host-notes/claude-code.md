# Claude Code host notes

Per-release notes on the Claude Code host, 2.1.234 through 2.1.302, as the maintainers reviewed them against this plugin. Source for every release: the official changelog, <https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md> (cited once here; every note below is drawn from it, plus the live runs recorded in `platform-targets.json`).

This file is the narrative. The **evidence-bearing record** is [`platform-targets.json`](../build-and-release/platform-targets.json) (`targets.claude_code`: `validated_against`, `reviewed_through`, `latest_known`, `verified_on`, and the per-cycle `verification_method` text), mirrored by the root [`.claude-code-version`](../../../.claude-code-version) pin, which `scripts/check-platform-version-pins.sh` holds to the JSON. When this file and that record disagree, the record wins. The nightly review appends to this file, never to `CLAUDE.md` (a `CLAUDE.md` at a plugin root is never loaded by Claude Code, `claude plugin validate` warns about it, and the plugin directory's scanner reads prose about what the plugin *used* to do as what it does).

**Reading a note.** Each release is a `### 2.1.NNN` heading; each item leads with the sub-topic in bold (Subagents, Hooks, Mods, MCP, Statusline, Monitor, Marketplace, Skill frontmatter, Eval suite, Remote and headless, Project instructions, Project memory, Security). From 2.1.288 on, each item also carries one of three marks:

- **adopted** — this repo changed something because of it (what, and in which plugin release);
- **reviewed, not applicable** — read against the tree and found to touch nothing here, with the reason recorded so nobody re-reviews it;
- **open** — relevant, deliberately not acted on yet, for Tamir's judgment.

Earlier notes (2.1.234–2.1.287) were written before the marks existed; their "adopted" / "reviewed and not applicable" wording is in the prose.

## 2.1.234 – 2.1.287

### 2.1.234

**Project memory —** `CLAUDE_CODE_PROJECT_DIR_NAME` overrides the per-project transcript directory name, which is otherwise *derived* from the clone's absolute path (`-Users-<you>-Projects-tamirs-superpowers`) and so shifts per machine/username and breaks if the clone moves. Adopted: `CLAUDE.md`'s Project memory section recommends pinning it (`export CLAUDE_CODE_PROJECT_DIR_NAME=tamirs-superpowers`) and the memory-restore snippet prefers the pin when set, falling back to the derived path, which assumes the standard `~/Projects/tamirs-superpowers` clone location.

### 2.1.243

**Subagents —** `/tasks` and the agent detail dialogs show which model and effort level each subagent ran on — useful for spot-checking `orchestrate-dev`/`worker-dev` fan-outs without instrumenting anything here. The same release fixed background subagents not waking when their last background Bash task finished; if a fanned-out worker previously seemed to hang after its shell command completed, that was a host bug, not this repo's orchestration.

### 2.1.246

**Subagents —** A subagent that stops because it hit its own `maxTurns` limit returns its output marked `partial` with a hint to continue it via `SendMessage`. This repo's own handoff vocabulary (`completed`/`partial`/`failed`/`blocked`, see [`worker-dev`](../../../skills/dev-workflow/worker-dev/SKILL.md)) already treats `partial` as "decide, never quietly integrate around it," so a `maxTurns`-truncated worker surfaces the same way a worker that self-reports `partial` does — no orchestrator change needed, but the label can now come from the host, not just from the worker's own handoff file.

### 2.1.247

**Subagents —** A subagent whose first model call 404s no longer dies outright — it falls back through the session's own fallback model chain with a detailed error, the same reliability class of fix as the two above; a fanned-out `worker-dev` task that previously looked like a hard failure on a transient model-routing error may now simply continue on a fallback model instead.

**Hooks —** Hook and background-task error output that previously could overflow the conversation with a "Prompt is too long" error, or leak memory unboundedly on repeated output-file write failures, is fixed host-side — relevant given the volume of hooks this plugin wires across `PreToolUse`/`PostToolUse`/`SessionStart`/`SessionEnd`/`UserPromptSubmit`/`StopFailure`/worktree events, though no hook here needed a change: none of them write to an unbounded log file themselves.

### 2.1.251

**Subagents —** `CLAUDE_CODE_SUBAGENT_MODEL` sets only the *default* subagent model instead of overriding every spawn: an agent definition's own `model:` field (every `agents/*.md` here pins one explicitly) and an explicit per-spawn model now take precedence over it. Before this fix, a user or CI environment exporting `CLAUDE_CODE_SUBAGENT_MODEL` could silently run every specialist agent on the wrong model regardless of its frontmatter pin; that can no longer happen.

**Hooks —** `SessionStart` payloads for a resumed or forked session can carry `seconds_since_last_response`/`context_tokens` (staleness) and `prompt_cache_likely_expired`/`estimated_cache_write_usd` (estimated re-cache cost). Adopted: `hooks/session-init.sh` adds a one-line `additionalContext` note when the resumed cache has likely expired, so that shows up before the first request re-caches rather than being inferred afterward from an unexplained cost/latency spike. The same release added `PreModelSwitch`/`PostModelSwitch` hook events (block, confirm, or annotate a model switch) — not wired here, since nothing in this repo's orchestration currently needs to gate or observe a model switch; noted for Tamir's judgment rather than wired speculatively.

**Statusline —** The payload can carry `rate_limits.spend_limit` (behind a Claude apps gateway with a spend limit configured). Adopted: `scripts/statusline.sh` renders it as a fourth line using the exact same only-when-present pattern as the existing 7-day line, so nobody outside a gateway with a spend limit configured sees any change. A `prompt_cache` block (`warm`, `hit_ratio`, `misses`, `recache_tokens_if_cold`) renders as a fifth line under the same rule — a host that does not report it prints nothing rather than a misleading `0%`, and the cold-rebuild token cost is shown only while the cache is actually cold. Schema and colour thresholds: [`statusline.md`](../statusline.md).

### 2.1.257

**Subagents —** `CLAUDE_CODE_SUBAGENT_MODEL_FORCE` is the deliberate opposite of the 2.1.251 fix: set it and every subagent runs on `CLAUDE_CODE_SUBAGENT_MODEL` (or the main model) regardless of an `agents/*.md` frontmatter `model:` pin or an explicit per-spawn model — the 2.1.251 guarantee holds only when `_FORCE` is unset. Nothing in this repo sets it; it is documented so a user or CI environment that does set it understands why a specialist agent is suddenly running on an unexpected model.

### 2.1.259

**Subagents —** Two related bugs fixed: auto mode no longer runs an unsupported model when an agent's frontmatter `model:` field names one, and interactive sessions no longer silently ignore that same field — both are exactly the `agents/*.md` `model:` pin this repo relies on (see 2.1.251/2.1.257), so this closes latent unreliability in a mechanism already documented here rather than requiring any change to it.

**Hooks —** A blocking `Stop` hook no longer discards the turn's reasoning or forces a prompt-cache miss on the next turn — relevant given `hooks/check-done.sh` runs on `Stop` and `hooks/handoff-reminder.sh`, `hooks/release-agent-claims.sh` and `hooks/session-end.sh` on `SessionEnd`, though none of them block by design (they inform; they never gate), so this removes a host-side cost/latency tax this repo was already avoiding rather than one it was paying. The same release also fixes worktree isolation refusing hook-created worktrees on some machines, and worktree-isolated sessions wrongly refusing Bash loops, `xargs` pipelines, and launcher-wrapped commands — `hooks/worktree-create.sh` creates every worktree here and `hooks/enforce-worktree-edits.sh` gates every `Edit`/`Write`/`MultiEdit`/`NotebookEdit` inside one, so both fixes land squarely on this repo's core-safety-invariant hooks; there was no repo-side workaround for either to remove, just fewer false-positive refusals going forward.

### 2.1.260

**Hooks —** `permissions.blockReadsOutsideWorkingDirectories` on macOS no longer hides the user's git config from sandboxed git, nor a worktree-isolated sub-agent's own checkout — this repo does not set that permission itself (it was reviewed and left out of `platforms/claude/settings.d/` in an earlier cycle as a personal auto-mode preference, not a plugin default), but the fix directly benefits worktree isolation for anyone who enables it alongside `hooks/worktree-create.sh`/`hooks/enforce-worktree-edits.sh`.

**Remote and headless —** `/reload-plugins` also works in headless (`-p`/SDK) sessions and appears in the Desktop/SDK command lists — previously interactive-only. Relevant to any headless automation, including this repo's own nightly platform-sync review, that dev-installs the plugin via `--plugin-dir` or a cache symlink and needs to pick up a local change without an interactive terminal.

### 2.1.261

**Hooks —** Resuming a session no longer loses hook output that was produced around parallel tool calls — relevant given the volume of hooks this plugin wires, though nothing here needed a workaround: no hook depended on output surviving a resume mid-parallel-call. The same release improved the host's dangerous-`rm` confirmation prompt to also catch `rm -rf` invoked on a positional parameter (e.g. `f="$1"; rm -rf "$f"`) rather than only a literal path — this is a built-in confirmation shown to the user before the tool call runs, independent of `PreToolUse` hooks, so it does not change what `hooks/enforce-worktree-edits.sh` or `hooks/guard-sensitive-files.sh` see; it is a second, host-side layer that now covers a shell pattern those hooks' PreToolUse matching does not specifically target.

### 2.1.265

**Subagents —** Resuming a foreground-spawned subagent no longer rewrites its tool list or system prompt and no longer breaks prompt-cache reuse — a `worker-dev` task that gets resumed mid-fan-out previously risked a silent tool-surface drift or a full re-cache cost on resume; neither can happen now. The same release fixed agent teammates and resumed subagents moving `SubagentStart` hook context out of the prompt prefix — this repo does not wire a `SubagentStart` hook (`hooks/hooks.json` declares `SessionStart`, `SessionEnd`, `PreToolUse`, `PostToolUse`, `Stop`, `StopFailure`, `SubagentStop`, `UserPromptSubmit`, `Notification`, `DirectoryAdded`, `WorktreeCreate` and `WorktreeRemove`, not `SubagentStart`), so the fix changes nothing here today but is worth knowing before anyone adds one. Also: a forked skill's kickoff prompt and text turns now stream as progress events instead of arriving silently — this repo ships exactly one forked skill, `targeted-debug` (`context: fork`, `agent: Explore`), so its fan-out is now visible turn-by-turn rather than looking idle until it returns.

**MCP —** An MCP server declared `"type": "http"` with only legacy HTTP+SSE support now auto-falls-back to that transport instead of never connecting — this repo's own server (`github`, via `scripts/github-mcp.sh`) is `stdio`, so the fix changes nothing here, but it is worth knowing before adding or recommending an `http`-type server in a downstream `.mcp.json`.

**Marketplace —** `--plugin-dir` also accepts a **folder of plugins** — each child folder with a manifest loads, and the set hot-reloads while running. This repo ships a single plugin, so the existing single-plugin `--plugin-dir .` form still applies unchanged; the folder form only matters to a contributor who develops this plugin alongside another local plugin in a shared parent directory, in which case pointing `--plugin-dir` at that parent picks up both.

### 2.1.267

**Skill frontmatter —** Before this release, `effort:` frontmatter on a custom command, skill or subagent was silently ignored on a model with a pinned default effort — every `effort:` value shipped here (twenty-nine `SKILL.md` files set it; no `agents/*.md` does) could have been a no-op on such a model, with no error surfaced. The fix makes the frontmatter authoritative again; no repo-side change is needed, but these values may not have taken effect before upgrading past it. The same release added `maxEffortLevel`, an org/user-configured ceiling on `/effort` — this repo does not set one (it is a host/account setting, not a plugin default), but a user or CI environment with a low `maxEffortLevel` will silently cap a skill's `effort: high` (`deliver-dev`, `orchestrate-dev`, `plan-dev`, `pr-dev`, `start-dev`, `switch-dev`, `worker-dev`, `cleanup`, `github-policy`, `multi-agent-repo`, `repo-scaffold`, `repo-standards`, `retro`, `platform-sync`) to whatever ceiling is set, the same way `CLAUDE_CODE_SUBAGENT_MODEL_FORCE` overrides an `agents/*.md` `model:` pin (see 2.1.257) — worth knowing rather than assuming a requested effort level was honored.

**Security —** Claude Code hardened marketplace entry-path handling against a backslash bypass of its symlink/containment check (mirroring an equivalent 2.1.265 fix for plugin paths). This is a host-side fix in Claude Code's marketplace-loading code, not something `Tamircohen28/tamirs-marketplace` or this repo's manifest can trigger or needs to change — recorded because this plugin ships *through* a marketplace listing, so the hardening is directly protective of its distribution path even though no action is required on this side.

### 2.1.268

**Hooks —** `PermissionRequest` hooks now fire in `--print` (headless) mode — not exercised here, since `hooks/hooks.json` wires no `PermissionRequest` event. `CLAUDE_CODE_SESSIONEND_HOOKS_TIMEOUT_MS` now actually extends a `SessionEnd` hook that declares no per-hook `timeout` of its own (previously still cancelled at 1.5 seconds regardless of the env var); every `SessionEnd` hook this repo ships (`session-end.sh`, `handoff-reminder.sh`, `release-agent-claims.sh`) already sets an explicit per-hook `timeout` in `hooks/hooks.json`, so this fix changes nothing here today, but matters before anyone adds a `SessionEnd` hook without one. The same release fixed `/mcp`/`/plugin` server details, `claude mcp list`/`get`, and MCP login errors showing a secret resolved from a `${VAR}` placeholder in an MCP config — this repo's `.mcp.json` passes the `github` server its token through `${user_config.github_token}` in the server's `env` (since 4.11.0; `scripts/github-mcp.sh` itself reads nothing off the machine, because the plugin directory's policy forbids a plugin forwarding a credential it found there), which is exactly the kind of resolved secret the fix keeps those surfaces from printing. And a respawned in-process teammate no longer picks up tools or a system prompt from a same-named agent file in an untrusted folder — this repo's `agents/*.md` live inside the trusted, versioned plugin checkout, so not a scenario this repo's own orchestration creates, but relevant to anyone fanning out `orchestrate-dev`/`worker-dev` from a workspace that also contains untrusted agent definitions.

**Marketplace —** Installing, enabling or disabling a plugin through the **interactive `/plugin` menu** takes effect as soon as the menu closes — `/reload-plugins` is no longer needed afterward. That is specifically about the menu flow, not about hand-editing plugin files during local development: `hooks/plugin-reload-reminder.sh` still reminds you to run `/reload-plugins` after editing `plugin.json`/`hooks.json`/`marketplace.json` under a `--plugin-dir` symlink, and that reminder is unaffected. The same release added `--json` to `claude plugin install`/`uninstall`/`update`/`enable`/`disable` (one machine-readable result line: `command`, `outcome`, `plugin`, `scope`, `message`, `failureCode`) and `errorDetails`/`noteDetails` to `claude plugin list --json` rows. Adopted: `scripts/update.sh` and `scripts/uninstall.sh` request `--json` from `claude plugin update`/`uninstall` and print the returned `message`/`failureCode` on failure, falling back to the previous generic instruction only if the CLI predates 2.1.268 or the output does not parse as JSON. It also fixed plugin/marketplace errors printing a token or password embedded in a git source URL, and hardened marketplace entry-path containment against a backslash bypass — both host-side, and this plugin's `marketplace.json` source is a plain `https://github.com/...` URL with no embedded credential, so neither was ever exposed here.

### 2.1.269

**Hooks —** A `PreToolUse` deny rule and the write-path check behind `Edit()` now also apply to a file a Bash `tee` command writes — previously a `tee`-based write could slip past a deny rule matched only against the editing tools — and a `Bash(tee:*)` allow rule is now scoped the way its glob implies instead of over-matching. This closes, at the host-permission layer, precisely the gap `hooks/guard-sensitive-files.sh`'s own header comment names and was built to cover independently: that hook keys on write *targets*, not the tool doing the writing, via `hooks/lib/write-targets.py`'s dedicated `tee` argument parsing, so it never depended on this host-level check being correct. `platforms/claude/settings.d/permissions-allow.json` and `permissions-ask.json` declare no `Bash(tee:*)` rule of either kind, so neither bug was ever exposed here — the host now simply agrees with what this repo's own hook already enforced. The same release fixed a deny/ask permission rule beginning with a bare `!` leaking beyond the settings source that declared it (a lone `!` is now ignored); reviewed against every rule in both permission files — none starts with `!`. And the attribution-reminder text that appends a `Co-Authored-By` trailer no longer overrides a project's `CLAUDE.md`/memory instruction against adding one — this repo's own instruction (see Commit trailer in `CLAUDE.md`) asks *for* the trailer, so the two policies were never in conflict, but a downstream fork that opts out via its own `CLAUDE.md` will now actually have that honored.

**Marketplace —** Plugin archives extracted for a session are no longer readable by other local users, no longer leave world-writable bits, and no longer leave stale files behind a re-extraction — host-side hardening of the extraction step itself, with nothing in this plugin's manifest or install path to change.

**Eval suite —** `claude plugin eval` runs a plugin's own eval suite (`evals/**/case.yaml` or `prompt.md` + `graders/*.md`) against the plugin and reports scored, reproducible results. Adopted: this repo ships one in [`evals/`](../../../evals/README.md): eight cases covering a single flow, `skill-creator`, each run with and without the plugin so the headline number is the uplift (Δ). It is a **different harness** from the per-skill `evals/evals.json`/`trigger-evals.json` pairs under `skills/toolkit/skill-creator/evals/`, which are that skill's own trigger-accuracy format (`scripts/run_eval.py`); the two coexist and are not interchangeable. Three things to know before running it. `Write`, `Edit` and `Bash` cannot be granted by a case's `allowed_tools` or by a skill's own `allowed-tools` frontmatter — only the operator's `--allow-tools` grants them, and that grant reaches **both arms**, which is what keeps Δ honest. Pass `--judge-model sonnet`: the default judge is the smallest model tier and marks correct-but-differently-formatted answers wrong. And never point a case at a path under `.claude/` — it is protected in the run sandbox, every write to it is denied, and the result looks exactly like the plugin failing (it cost this suite a full calibration cycle to find). The suite's own calibrated findings, including a real Δ −0.25 regression on `fix-weak-description` and a `context: fork` gap that fails in both arms, are recorded in [`evals/README.md`](../../../evals/README.md).

**Remote and headless —** `/output-style [name]` can list or switch output styles over Remote Control and in cloud/headless sessions too — an interactive convenience with nothing for this repo's manifest to adopt. The same release fixed two other headless/remote paths that do not apply to this repo today: organization plugins distributed via managed settings not loading in headless sessions (this plugin is installed by a user running `/plugin marketplace add` + `/plugin install`, not pushed via an org's managed settings), and a synced plugin's MCP servers not reconnecting when a remote session resumes (the one server this plugin declares, `github`, is its own stdio server bundled with the plugin, not a separately "synced" one) — both recorded in case a future distribution model for this plugin ever does route through either mechanism.

### 2.1.270

**Hooks —** A regression in 2.1.269, fixed the next day: read-only git commands in Bash no longer unexpectedly ask for permission after a session has been running for a while — relevant because `permissions-allow.json` deliberately pre-allows several git commands (`git add`, `git commit`, `git push`, `git tag`, `git remote add`, `git init`) specifically to avoid this class of friction; nothing here needed a workaround, but a session that hit the regression mid-cycle would have seen exactly the prompt this pre-allow list exists to prevent.

### 2.1.271

**Subagents —** Agent frontmatter (and `--agents` JSON) gained `omitClaudeMd`, letting a custom or plugin subagent run without the user/project/local `CLAUDE.md` files loading (managed policy files still load). Reviewed against all ten `agents/*.md` here and deliberately left unset: every one of them already loads its own canonical contract explicitly via a relative link to `core/roles/*.md` and `core/policies/*.md` rather than depending on `CLAUDE.md` for that, but each still relies on the *target* project's own `CLAUDE.md` for the domain conventions a role judges against — `implementer` matching house style, `security-reviewer` knowing a project's declared security posture, and so on. Setting `omitClaudeMd: true` would cut every one of them off from exactly the context they need, so this is recorded as reviewed-and-declined, not silently skipped.

**Hooks —** A stale `.git/config.lock` left behind after a sandboxed Bash command failed to start no longer breaks `git checkout -b`, `git push -u` or `git config` for the rest of the session (Linux) — directly relevant, since `permissions-allow.json`'s pre-allowed `git push *`/`git remote add *`/`git init` and `hooks/worktree-create.sh`'s `git worktree add -B` both run through the same sandboxed Bash surface this bug affected; no repo-side workaround existed, so a session that hit it on Linux previously had to restart to regain reliable git access, and now doesn't. The same release fixed Claude starting a second copy of a background command (such as a watch loop) that was still running after the conversation was compacted — relevant to a long `orchestrate-dev`/`worker-dev` fan-out that compacts mid-run with a background task in flight; host-side fix, nothing here to change. And cross-session messages held by the receiving session's permission-mode policy no longer vanish without a trace: a headless sender now gets a delivery notice, and a `SendMessage` result no longer implies the message was read — this extends the cross-session `SendMessage` reliability work already tracked in [`docs/user/cross-platform-workflow.md`](../../user/cross-platform-workflow.md), see that file for the dated note.

**Monitor —** Every `Monitor` watch now always carries a deadline — at most 30 minutes (10 in single-prompt `-p` runs) — and Claude is notified to re-arm it, replacing the old no-timeout `persistent` option entirely; this repo's one documented `Monitor` call ([`pr-dev`'s CI-rollup wrapper](../../../skills/dev-workflow/pr-dev/references/ci-monitor-loop.md), `timeout_ms: 1800000`, no `persistent` flag) was already inside that ceiling and never set `persistent`, so nothing here needed to change. The same release added per-command `allowed_domains` to `Bash`, `PowerShell` and `Monitor` in auto mode with sandboxing (only the hosts a command needs are reviewed and opened for it) — reviewed against `platforms/claude/settings.d/`: no `PowerShell` rules ship here, no `Bash` rule is network-scoped beyond `gh`/`git`'s own auth, and no doc here recommends running this plugin under auto mode with sandboxing, so there is no `allowed_domains` list to declare.

**Marketplace —** `claude plugin install`/`claude plugin update` accept `--accept-command <sha256>` to confirm exactly the command a previous `--json` run displayed, instead of the blanket `-y`. Reviewed against `scripts/update.sh`'s and `scripts/uninstall.sh`'s existing `claude plugin update`/`uninstall ... --json` calls (added for the 2.1.268 `--json` diagnostics): neither script passes `-y` or hits an interactive confirmation today, so there is no blanket-accept behavior here for `--accept-command` to tighten — not adopted, recorded rather than silently skipped.

**Remote and headless —** Fast mode is available in Claude Code Remote sessions (cloud and self-hosted runners): the host's fast-mode setting or `/fast` typed in the session applies where the organization allows it — an interactive/account-tier convenience with nothing for this repo's manifest to adopt.

### 2.1.272

Bug-fixes-and-reliability-only, per the official changelog — nothing to record.

### 2.1.273

**Hooks —** Reverts a 2.1.268 change that had started checking `Read`/`Edit` deny rules on Bash lines the permission checker cannot fully analyze (`eval`, `env -C`, and similar): such a line now prompts for approval again instead of being silently denied. Neither `permissions-allow.json` nor `permissions-ask.json` here name an `eval`/`env -C` rule pattern, so this changes generic host behavior, not anything this repo declares — reviewed and found not applicable.

### 2.1.274

**Subagents —** A sub-agent's progress summary is no longer replaced by a runaway multi-paragraph reply — directly relevant to this plugin's own handoff vocabulary (`completed`/`partial`/`failed`/`blocked`, see [`worker-dev`](../../../skills/dev-workflow/worker-dev/SKILL.md)) and any `orchestrate-dev` fan-out that reads a worker's summary back to decide what happened, since a runaway reply previously risked obscuring exactly the status line that vocabulary depends on. The same release fixed `claude agents` (the standalone CLI subcommand, distinct from the in-session `Agent` tool) losing `--model`/`--effort`/`--permission-mode`/`--allow-dangerously-skip-permissions`/`--agent` after an auto-update — no script here shells out to `claude agents` directly, so this is not exercised by anything in the repo, but it is relevant to a contributor invoking one of the ten `agents/*.md` from that CLI subcommand by hand with an explicit flag. Also reviewed and not applicable: a fix for a subagent pinned to the `opus` alias leaving the wrong session model behind on Bedrock/Vertex/Foundry — every `agents/*.md` here pins the same other alias, and this repo targets direct Claude Code/Desktop sessions, not a Bedrock/Vertex/Foundry gateway.

**MCP —** `CLAUDE_CODE_MCP_STARTUP_WAIT_MS` extends how long the host waits for a slow-starting MCP server before giving up on it — worth setting if `scripts/github-mcp.sh`'s Docker fallback path (`docker run ... ghcr.io/github/github-mcp-server stdio`) is slow to start on your machine, e.g. after a cold image pull; this is not set as a repo default, since the right wait time is workstation-dependent, not something the plugin can know in advance. The same release switched Bedrock/Vertex/Foundry and telemetry-disabled sessions to MCP client v2 by default — not applicable here, since this repo targets direct Claude Code/Desktop sessions rather than a Bedrock/Vertex/Foundry gateway.

### 2.1.275

**Marketplace —** `/plugin install <plugin> --marketplace <source>` installs from a named marketplace in one step; reviewed against the two-step `/plugin marketplace add` + `/plugin install` sequence that `CLAUDE.md` and [`docs/user/install/claude-code.md`](../../user/install/claude-code.md) documented, and left as a Future opportunity in that cycle since the two-step form still works (the docs later switched to leading with the one-step form — see 2.1.295). The same release added syncing of skills and plugins enabled on a user's claude.ai account into their terminal sessions, opt-out per-kind via the `syncClaudeAiSkills: false` / `syncClaudeAiPlugins: false` settings — worth knowing if a name collision ever shows up between a synced claude.ai skill and one of this plugin's 29 `SKILL.md` names, since the opt-out is how you would resolve it. It also fixed plugin/marketplace messages leaking a secret embedded in a URL (host-side; this plugin's `marketplace.json` source is a plain credential-free `https://github.com/...` URL, so nothing here was ever exposed) and fixed `claude plugin marketplace update` deleting the local marketplace copy on a failed fetch — directly relevant to the `/plugin marketplace update tamirs-marketplace` step documented in `CLAUDE.md`, since a flaky fetch previously risked wiping the installed cache instead of leaving it untouched; no repo-side workaround existed for that, and none is needed now.

### 2.1.277

**Subagents —** The deprecated `TaskOutput` tool is removed — grepped every `agents/*.md` `tools:` line and every skill/hook/doc in this repo for `TaskOutput`; zero references, so nothing here relied on it.

**Project instructions —** A project with no `CLAUDE.md` at all now has Claude Code read its `AGENTS.md` instead, configurable under "Project instructions" in `/config`. This repo's own root always ships both files, and `repo-scaffold`/`multi-agent-repo` always scaffold both together for any new target repo they generate (see the Root file checklist in [`repo-scaffold`](../../../skills/repo/repo-scaffold/SKILL.md)), so no project this toolkit touches or creates is ever missing a `CLAUDE.md` for the fallback to actually engage on — reviewed and recorded as not applicable, not silently skipped. It is still worth knowing before recommending this toolkit's specialist `agents/*.md` (each of which reads the *target* project's own `CLAUDE.md` for domain conventions, see the 2.1.271 `omitClaudeMd` note) against a third-party repo that ships only an `AGENTS.md`: since 2.1.277, that repo's instructions now load automatically where they previously would not have.

### 2.1.278
