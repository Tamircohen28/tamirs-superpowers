# V5 upgrade and refactor plan

**Status:** proposal, 2026-10-17. Written against plugin 4.12.2 (master `2d9ee21`), Claude Code 2.1.302, Codex 0.163.0, Cursor desktop 3.24, Gemini CLI 0.64.0, OpenCode 2.0.32. The per-platform research notes it cites are in [`v5-research/`](v5-research/). Claims the research could read but not run live are flagged in the text; the risk register at the end lists them.


tamirs-superpowers 4.12.2 is current on paper and stale in practice: it pins Claude Code 2.1.287 while the host is at **2.1.302**, Codex 0.160.1 against **0.163.0**, Cursor 3.23.12 against desktop **3.24**, Gemini CLI 0.62.0 against **0.64.0**, and OpenCode 2.0.24 against **2.0.32** — and the research shows that three of those gaps hide genuine breakage rather than cosmetic drift. The Claude Code "mods" feature the plugin adopted in 4.10.0 is an in-process hooks module (`hooks/hooks.json` `modules` → `mod/register.tsx`) that the plugin uses at roughly a fifth of its surface: 14 event registrations and 14 `$` methods out of ~45 events, 22 namespaces and ~70 methods, with the ten releases since launch adding `prompt.autocomplete`, `$.ui.notify`, `$.ui.view`, `skill.prompt` frontmatter, `agent.spawn` for teammates, `$.store` cross-session state and fail-closed semantics that the mod does not yet exploit ([Mods reference](https://code.claude.com/docs/en/plugins/mods/reference); [CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)). On the other four platforms the audit answer is "no, and in three cases the current files are wrong": Codex's `HooksFile` parser is `#[serde(deny_unknown_fields)]`, so the `modules` key the plugin ships in the very `hooks/hooks.json` Codex loads is now source-confirmed to fail parsing ([hook_config.rs](https://raw.githubusercontent.com/openai/codex/main/codex-rs/config/src/hook_config.rs)); OpenCode 2 states that "V1 plugin implementations do not run in V2" and has deprecated the 15-key `permission` object the plugin's generator and `check-opencode-permission-keys.sh` are pinned to ([migrate-v1](https://opencode.ai/v2/docs/build/plugins/migrate-v1/); [config.json](https://opencode.ai/config.json)); Google retired Gemini CLI for every consumer tier on June 18, 2026 in favour of Antigravity CLI, which imports extensions as a different plugin format ([Google Developers Blog](https://developers.googleblog.com/en/an-important-update-transitioning-gemini-cli-to-antigravity-cli/)); and the Agent Plugins 1.0 root `plugin.json` that Codex, Cursor, Copilot and Kiro now read is absent from the repo ([agent-plugins-spec 1.0.0](https://github.com/agentplugins/agent-plugins-spec/blob/main/spec/1.0.0.md)). A V5 that earns its major number therefore does four things: raises the Claude Code floor to the mods era and extends the mod into guards, autocomplete, cross-session state and agent dashboards; replaces the hand-synced per-host manifests with a one-source, N-target build that emits a conformant Agent Plugins package plus Claude, Codex, Cursor, Antigravity and OpenCode-V2 subsets; splits the 28-hook monolith into tiered plugins so safety stays on and contributor noise goes off by default; and adds the trust layer no peer ships — signed releases, an always-on token budget, cross-host hook conformance tests and evals in CI. The phased plan, breaking changes, migration notes and a risk register follow; the two open nightly PRs (#271, #277) and the daily drift issues #270–#283 are the first thing to land, because every later phase builds on their baselines.

## Claude Code moved fifteen releases past the pin, and three of them change hook semantics

The plugin's `.claude-code-version` and `docs/engineering/build-and-release/platform-targets.json` both say 2.1.287; npm `latest` is **2.1.302** (2026-10-16), `stable` is **2.1.292**, and 2.1.297/2.1.298 were never published ([npm registry](https://registry.npmjs.org/@anthropic-ai/claude-code)). The unmerged PR #271 (`claude-code-update`) already reaches 2.1.300 and fixes a real regression — `turn.start` zeroing `writesThisTurn` for subagent turns, because since 2.1.299 that hook "also hear[s] subagents' and teammates' turns" and must be told apart by `e.agentId` ([CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)). Three semantic changes in the range matter for the plugin's bash hooks regardless of the mod. First, **2.1.299 moved `UserPromptSubmit` to run before a skill or slash command expands**, so `hooks/goal-condition-lint.sh`, `hooks/skill-suggest.sh`, `hooks/scope-decompose-reminder.sh` and `hooks/capture-task-slug.sh` now see the raw `/name args` text rather than the expanded skill body, and a skill's own frontmatter `UserPromptSubmit` hook "first run[s] on the prompt after the one that invokes the skill" ([CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)). Second, **2.1.299 made plugin-hook-blockable actions "refused, not let through" when the hook cannot be handed the event or cannot hand back its answer**, and 2.1.295 added `onFailure: "block"` for command and HTTP hooks so a guard that "can't start, times out, or exits with an unexpected code blocks the action instead of letting it through" ([Hooks reference](https://code.claude.com/docs/en/hooks)). The four core-safety-invariant guards (`enforce-worktree-edits.sh`, `guard-sensitive-files.sh`, `protect-other-branches.sh`, `docker-guard.py`) were written fail-open; PR #271 records `onFailure: "block"` as a pending decision, and the research settles it in favour of adopting it, since the mod path already fails closed. Third, **2.1.300 validates `updatedInput` from `PreToolUse`/`PermissionRequest` hooks "like Claude's own input: unknown keys are dropped, and input the tool rejects denies the call"** — none of the four guards rewrite input today, so this is a constraint on future work rather than a breakage, but any hook that passes hints through invented keys will silently lose them ([CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)).

Two narrowing changes in 2.1.299 are the likeliest silent breakages for any existing plugin: MCP allow rules now "reach only the server they name: `mcp__a` no longer allows `a__b` or `a_`", and agent `tools:` lists "take only the named MCP server's tools; list a server whose name contains `__` as `mcp__<whole name>__*`" ([CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)). `agents/research-agent.md` names `mcp__claude_ai_Context7__resolve-library-id` and `mcp__claude_ai_Context7__query-docs` — exact tool names, so they survive — but `platforms/claude/settings.d/permissions-allow.json` and `permissions-ask.json` must be grepped for any bare `mcp__github` form before V5 ships, and the generated `.opencode/agent/*.md` and `.gemini/agents/*.md` translations should be re-derived from the same source once the rule is audited. The rest of the range is additive and mostly good news: `WorktreeCreate`/`WorktreeRemove` plugin hooks finally run under `--worktree` (2.1.300, "not yet with `--tmux`"), so `hooks/worktree-create.sh` now reaches a surface it previously missed; `SessionEnd` hooks run when exiting with a background command still running (2.1.300); the permission prompt for a plugin hook's `ask` now names the plugin (2.1.301); `claude plugin install --marketplace <source>` is the one-step install (2.1.292) that PR #271's docs adopt; the Agent tool gained an `effort` parameter overriding frontmatter `effort` (2.1.292); subagent frontmatter gained `autoCompactWindow` (100000–1000000, 2.1.296); subagents preload at most 32 skills (2.1.295); `agentType` reached the `subagentStatusLine` payload (2.1.293); at most 12 prompt/agent hooks of one event run concurrently (2.1.302); fork subagents are on by default in `-p`, SDK, Desktop and VS Code (2.1.302); and stdio MCP servers negotiate protocol 2026-07-28 by default from 2.1.292 with `MCP_PROTOCOL_NEGOTIATION=legacy` as the opt-out ([CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md); [Sub-agents docs](https://code.claude.com/docs/en/sub-agents)). That last item touches `scripts/github-mcp.sh`: GitHub announced its MCP server supports "the next MCP specification" on 2026-07-23, so the Docker fallback image and any pinned binary should be checked for a build that negotiates 2026-07-28 cleanly, because 2.1.302 had to fix "MCP servers showing no tools when negotiating protocol 2026-07-28 but omitting `resultType`, `ttlMs` or `cacheScope`" ([github.blog](https://github.blog/changelog/2026-07-23-github-mcp-server-supports-the-next-mcp-specification/); [CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)).

One manifest-reference rule deserves its own line because the plugin violates it today: "A `CLAUDE.md` at the plugin root isn't loaded and `claude plugin validate` warns about it", and the local validate run on 2.1.302 printed exactly that warning ([Manifest reference](https://code.claude.com/docs/en/plugins-reference)). The root `CLAUDE.md` is 51.8 KB, almost entirely per-host-release notes from 2.1.234 to 2.1.287, and `docs/engineering/build-and-release/directory-distribution.md` records that the directory's scanner "reads prose about what the plugin *used* to do as what it does". The `claude` tag build strips `AGENTS.md`, `CHANGELOG.md` and `docs/engineering/` for that reason but keeps `CLAUDE.md`; V5 should move the host-version narrative into `docs/engineering/host-notes/<platform>.md` (excluded from every distribution), leave `CLAUDE.md` as a short contributor pointer, and let `platform-targets.json` remain the single evidence-bearing record. The same facts are currently restated in `CLAUDE.md`, `platform-targets.json` `verification_method` strings, `core/capabilities/platforms.json` `notes`, and `CHANGELOG.md` — four copies that `check-doc-claims.sh` and `check-platform-targets.sh` check only for counts and versions, never for narrative drift.

## Mods run in-process on three surfaces; the plugin uses a fifth of the API

A mod is "a plugin that changes how Claude Code looks and behaves", made of "JavaScript or TypeScript event handlers" that can "watch the event, change it, or take it over"; it is declared by a `modules` array in `hooks/hooks.json` naming one ES module that exports `register(on, options)`, with `options` holding the manifest's `userConfig` values and an optional `types/index.d.ts` (manifest key `types`) declaring the `$.state` contract ([Mods overview](https://code.claude.com/docs/en/plugins/mods); [Mods reference](https://code.claude.com/docs/en/plugins/mods/reference)). The module "runs in an environment of its own, with no DOM and no Node: everything outside it is reached through `$`"; it has "no Node.js APIs, no timer globals such as `setTimeout`, and no network or file access of its own", may import only relative files plus the bare `claude-code`, and shares one worker thread with every other installed mod — a mod that crashes that worker is unloaded, and three untraceable crashes turn every non-built-in mod off for the session ([Mods API](https://code.claude.com/docs/en/plugins/mods/api); [Troubleshoot](https://code.claude.com/docs/en/plugins/mods/troubleshoot)). Mods are on by default from 2.1.287 in the terminal (2.1.286 in Desktop's bundled CLI); `CLAUDE_CODE_ENABLE_FUNCTION_HOOKS` is ignored from 2.1.287; and the where-it-runs table is the key operational fact: hooks run everywhere (terminal, Desktop Code tab, VS Code panel, `claude -p`, SDK, cloud, Remote Control, Bedrock/Vertex/Foundry), but drawings appear only in the terminal, the Desktop Code tab, and — since extension 2.1.299 — the VS Code chat panel; Desktop WSL sessions get neither ([Mods overview](https://code.claude.com/docs/en/plugins/mods)). Six built-in mods ship with the CLI (`cc-plugin-agents-md`, `cc-plugin-diff`, `cc-plugin-plugin-authoring`, `cc-plugin-sec-default`, `cc-plugin-telemetry`, `cc-plugin-you-should-know`) and four of them are public source under `anthropics/claude-code/mods`, which is the best reference for house style: each has tests named for the file they cover, uses `claude-code/testing`, and `tsc -p mods/tsconfig.json` ([MODSRC](https://github.com/anthropics/claude-code/tree/main/mods)). Six further `cc-plugin-*` ids (`claude-test`, `easel`, `mermaid`, `mods-guide`, `responsive-mode`, `tips`) appear as strings in the 2.1.302 binary — a local observation, undocumented, flagged as unconfirmed.

### What `mod/register.tsx` uses today

The 510-line module registers 14 hooks — `session.start`; `command.run{command:'objective'}`; `ui.render{Pane, requestId:'objective'}`; `agent.spawn`; `ui.render{Spinner}`; `ui.render{UserMessage, props.origin.kind:'task-notification'}`; `session.measure`; `ui.render{AbovePrompt}`; `prompt.submit`; `turn.start`; `tool.call`; `turn.complete`; `session.compact`; `attribution.text{kind:'commit'}` — and calls 14 `$` methods: `$.clock.every/now`, `$.command.register`, `$.env.get` (`OBJECTIVES_ROOT`, `SUPERPOWERS_OBJECTIVE_STATE_DIRNAME`, `SUPERPOWERS_OBJECTIVE_ID`), `$.fs.exists/list/read`, `$.model.classify`, `$.session.repo/root`, `$.ui.invalidate/open/resolve/toast`, plus `$.state` through `atom/read/update` with five atoms (`objective`, `usage`, `limitWarning`, `dismissedAtPercent`, `workers`). It delivers six features: the objective pane and `/objective` (`immediate`), worker count on the spinner, the rate-limit band at `rate_limit_warn_percent` (default 85) driven by `session.measure`, the Desktop-only usage line, opt-in `semantic_skill_suggest`, and the DoD line, compaction snapshot and commit-trailer enforcement. It deliberately does not touch `$.process`, `$.http`, `$.fs.write/stat`, `$.tool.register`, `$.session.append/usage/send`, `$.ui.view/selection/notify/status/ask`, `$.store`, `prompt.change`, `tool.check`, `skill.prompt`, `prompt.autocomplete`, `classic.*`, or any permission decision — a footprint shaped by the Anthropic directory review, whose `MOD_*` codes (recorded only in this repo's own `docs/engineering/architecture/mods.md` and `directory-distribution.md`, never in a public page) block `MOD_CAPABILITY_USE_NOT_PLAIN` and `MOD_FORWARDS_CREDENTIAL_ENV` and hold `MOD_RUNS_PROCESS`, `MOD_DATA_LEAVES_BY_PROMPT` ("A mod that reads files and can submit a prompt is held whatever it submits"), `MOD_ANSWERS_PERMISSION` and `MOD_HOOKS_POLICY_EVENT`. Four facts in the checked-out tree are stale against the research: the header's "handoff button submits a fixed prompt" sentence (4.11.6 removed the button); `mods.md`'s "three non-sensitive userConfig fields" (two remain after 4.11.1 dropped `pushover_min_turn_seconds`); `mods.md` row 6 still naming `$.process.run` and "uncommitted files" (removed in 4.11.0); and test counts of 23/24 in `mods.md` and `platform-targets.json` against 21 in `mod/mods.test.tsx` (22 on PR #271). The local `claude plugin validate .claude-plugin/plugin.json` on 2.1.302 also prints four `gating hook without .catch` lines (`agent.spawn`, `prompt.submit`, `tool.call`, `session.compact`) and a new 2.1.299 note that "hooks on session.compact, attribution.text do not run in a plugin a person installs where an organization manages Claude Code" — the bash `precompact-snapshot.sh` fallback covers the first, and the commit-trailer prose in `CLAUDE.md` covers the second, which should be stated in `mods.md`.

### What changed between 2.1.287 and 2.1.302

The API gained roughly ten methods and events in fifteen days, none of them namespaces, so a 2.1.288-typed mod still typechecks for what it already uses ([Mods reference](https://code.claude.com/docs/en/plugins/mods/reference); [CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)):

| Release | Addition | Relevance to this mod |
|---|---|---|
| 2.1.288 | `$.ui.selection()` (fullscreen terminal) | low |
| 2.1.289 | `agent.spawn` for teammates (`e.isTeammate`), one agent id across events, `idle`/`waiting` in `$.agent.list()`, `ui.fault` | objective pane can show teammate state |
| 2.1.290 | `tool.check` `e.agentId`/`e.ceiling`, `prompt.mention`, `serverToolUses` on `turn.step`, `ThemeKey`/`Color` types, validate lists gating hooks with/without `.catch` | theme-safe colours; `.catch` audit |
| 2.1.292 | `prompt.autocomplete` (`{ suggestions }` of `{ text, label, description }`), workflow agents in `agent.spawn`, cache-breakpoint blocks in `$.model.complete`, `next.error.kind: 're-entry'`, 4,096-char reason cut | skill/command completion; cheaper classify |
| 2.1.293 | `isDeferred` on `$.tool.register`, `mock.session` in tests | an `objective_status` tool |
| 2.1.295 | `$.ui.notify` (native notification), `Button` children, hot-reload fixes | rate-limit band can notify |
| 2.1.296 | served `$` methods run in the calling agent's cwd; stale `$.agent.register` refused | worker-scoped reads |
| 2.1.299 | `Text` `size`/`weight`/`mono`/`tabular`, `Box` spacing steps `xs`–`xl` (`bold` deprecated), `skill.prompt` gains `e.source`/`e.pluginName`/`e.path`/`e.frontmatter`, `session.append` `queue` door, VS Code rendering, `turn.start` for subagent turns, `agent.spawn` `resume`, `part: { plugin }` on test render roots, `$.prompt.media`/`$.session.identity()` (managed only) | typography; skill-expansion context; **test breakage** |
| 2.1.300 | `virtualText` prompt decorations, `$.ui.view({ agentId })`, `prompt.change`, `Text` `dir`, workflow `prompt`/`model` rewrite in `agent.spawn`, `next.error.cause: 'rewritten'` | jump-to-worker; inline hint |
| 2.1.301 | `Input` `rows`, `$.env.set` resolves `{}`/`{ deny }`, `.catch` only on throw/timeout, Markdown above the question dialog on Desktop/VS Code/mobile | multi-line handoff note |

Two of these are breaking for the existing test file: trees using `weight` or spacing step names do not draw on a release earlier than 2.1.299 ("Claude Code draws its own version of the site"), and from 2.1.299 "each mod's Box/Text root now carries `part: { plugin }`, so exact-tree assertions must include it" ([Mods reference](https://code.claude.com/docs/en/plugins/mods/reference); [CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)). The stable npm channel sits at 2.1.292, so any adoption of a 2.1.293+ feature meets users without it; the safe pattern is to branch on `$.session.version()` (a `$.session` method listed in the 2.1.288 d.ts) or on feature presence and keep the 2.1.287 tree as the fallback until V5's minimum rises.

### Enhancements mods make possible that bash hooks cannot

The research supports a concrete catalogue, ranked by value against directory risk. Everything in the first group preserves the mod's current low-scrutiny footprint (no `$.process`, no `$.http`, no `$.prompt.submit`, no permission answer).

**Fail-closed `.catch` on the four gating hooks** (PR #271 already does this): add `.catch(($, e, next) => next(e))` so a timeout or throw neither blocks a tool call the mod never meant to gate nor reads to a reviewer as a policy-answering hook; from 2.1.301 `.catch` runs only on throw or timeout ([Create](https://code.claude.com/docs/en/plugins/mods/create)). **`classic.SessionStart { source: ['clear','resume','fork'] }`** to reload `$.state` after `/clear`, `/resume` or `/branch`, which reset state while `session.start` does not fire — today the objective pane goes blank until the 5-second re-read and `dismissedAtPercent` forgets its dismissal ([Interface](https://code.claude.com/docs/en/plugins/mods/interface)). **`$.store`** for the two values that should survive a session: the skill-suggest "once per label" set (today per load) and the rate-limit dismissal, since `$.store` is "a JSON KV that every session on the machine shares" under `~/.claude/plugins/store/`, 4 MiB, with the documented re-read-before-write discipline ([Interface](https://code.claude.com/docs/en/plugins/mods/interface)). **`prompt.autocomplete`** (2.1.292) returning the 26 public skill names, `/objective`, and `/switch-dev handoff` as `{ text, label, description }` rows — a discoverability surface no bash hook has, and one that directly attacks the "zero invocations across 953 sessions" failure mode `CLAUDE.md` records for `switch-dev` ([CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)). **`skill.prompt`** with the 2.1.299 fields: when a `dev-workflow` skill of this plugin expands (`e.pluginName === 'tamirs-superpowers'`, `e.frontmatter`), append the live objective id, active worktree and open task count to `{ text }`, so `worker-dev` and `orchestrate-dev` start every run with state the bash `objective-state.sh show` otherwise has to be asked for ([Mods reference](https://code.claude.com/docs/en/plugins/mods/reference)). **`$.tool.register({ name: 'objective_status', isDeferred: false })`** answered by `tool.call{ tool: 'mcp__tamirs-superpowers__objective_status' }` reading the same `.dev-files/objectives/<id>/` JSON — a model-callable, Bash-free read of orchestration state, listed upfront rather than behind tool search ([Mods API](https://code.claude.com/docs/en/plugins/mods/api)). **`$.agent.list()`** statuses (`pending`, `running`, `waiting`, `idle`, `completed`, `failed`, `killed`) rendered in the objective pane with a `Button` per task row whose press calls **`$.ui.view({ agentId })`** (2.1.300) to open that worker's transcript — the "swarm"/"agent-flow" category that claudemods.chat lists as one of the most popular mod types, here keyed to the plugin's own task files ([claudemods.chat](https://claudemods.chat/)). **`$.ui.notify`** (2.1.295) from the rate-limit band so the warning reaches the user through their own notification setting without the mod making a network call — complementary to, not replacing, `scripts/notify-pushover.sh`. **`virtualText`** (2.1.300) to decorate the prompt box with "type /switch-dev handoff" instead of only the band, and `$.prompt.fill({ text: '/switch-dev handoff', mode: 'insert' })` behind a `Button` — fill is not submit, but whether the directory reads a fill the same way it reads `MOD_DATA_LEAVES_BY_PROMPT` is unverified and must be asked before shipping. **`command.describe`/`config.describe`** to give `/objective` an `argumentHint` and the two options readable labels. **VS Code surface handling**: the mod branches on `e.surface === 'desktop'`; from extension 2.1.299 `vscode` draws too, ignores `Button` `hotkey`/`plain`/`autoFocus`/`action`, `Text` `size`/`mono`/`tabular`, `Box` `position`/`hover` and `Code` styling, cuts status lines at 200 and toasts at 500 characters, and never renders `Client` — the band and pane need a third branch and a `claude plugin test` loop over `['terminal','desktop','vscode']` ([Mods reference](https://code.claude.com/docs/en/plugins/mods/reference)).

The second group changes the footprint and needs a directory decision first. A **`blast-radius`-style hold** — `tool.call{ tool: 'Bash' }` matching force-push, `rm -rf`, `git worktree remove` and `git branch -D`, pausing in `$.ui.ask` with the guard's own reason and buttons to proceed or cancel — is exactly what Anthropic's own sample mod does and what `hooks/guard-sensitive-files.sh` cannot (bash can deny, not hold), but a hook that can deny reads as `MOD_HOOKS_POLICY_EVENT` ([playground](https://github.com/anthropics/claude-code-playground/tree/main/claude-code/mods)). **`tool.check`** returning `{ decision: 'deny' }` for a write outside the active worktree would mirror `enforce-worktree-edits.sh` in-process and also "approve a call that a `PreToolUse` hook outside managed settings blocked" — powerful, and precisely `MOD_ANSWERS_PERMISSION` ([Events](https://code.claude.com/docs/en/plugins/mods/events)). **`agent.spawn` → `next({ ...e, model })`** to enforce the `model: sonnet` pin on every worker regardless of `CLAUDE_CODE_SUBAGENT_MODEL_FORCE` is the same class. The research's recommendation is structural rather than a refusal: ship these as a **separate marketplace plugin** (`tamirs-superpowers-guard`) with its own `hooks/hooks.json` `modules`, so the core plugin keeps its clean `calls:` line in the directory while users who want in-process holds install the guard plugin from the marketplace, where the directory's holds do not apply. The spec allows one module per `hooks/hooks.json` ("an array with one path"), which is itself a reason the split must be at plugin granularity ([Mods reference](https://code.claude.com/docs/en/plugins/mods/reference)).

Two further mod-layer facts shape the plan. Settings-hook events are reachable as `classic.<Event>` with the hook's stdin JSON as `e`, so `classic.PreModelSwitch`/`classic.PostModelSwitch` are the inferred route to the model-switch events `CLAUDE.md` left "for Tamir's judgment" — inferred, since no page names them ([Mods reference](https://code.claude.com/docs/en/plugins/mods/reference)). And `${CLAUDE_PLUGIN_DATA}`/`CLAUDE_PLUGIN_ROOT` are not mentioned in any mods page; whether `$.env.get` sees them inside the hooks worker is an open gap, so a mod sharing state with the bash hooks must agree a path through `$.session.repo()` rather than the plugin-data directory.

### Refactor plan for the mod

The plan keeps the architectural rule in `docs/engineering/architecture/mods.md` — the mod does only what bash cannot, every guard stays canonical in bash — and adds structure. Split `mod/register.tsx` into `mod/register.tsx` (every `on(...)` and every `$` call), `mod/objective.ts` (pure readers of `.dev-files/objectives` JSON), `mod/usage.ts` (band/line formatting), `mod/skills.ts` (`SKILL_LABELS`, autocomplete rows), and `mod/compat.ts` (version gates), because the validator allows relative imports of pure helpers while requiring `$` to be "written in full" at the call site; note the documentation conflict that passing `$` to "a function you import from another of your files fails validation" while the 2.1.299 changelog says validate now accepts "`$` handed to a function declaration imported from another file" — keep `$` in one file and the question moot ([Create](https://code.claude.com/docs/en/plugins/mods/create); [CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)). ## Codex rejects the `modules` key and the directory refuses hooks

Eight Codex stable releases shipped between 0.156.0 (22 Sep) and 0.163.0 (15 Oct 2026), none changing the plugin manifest, the hook event list or the SKILL.md contract ([Releases](https://github.com/openai/codex/releases?q=rust-v0.16&expanded=true)). The plugin-relevant runtime changes are hook matchers compiled at discovery and MCP-hook placeholder caching (0.161.0), ANSI in hook `systemMessage` and `statusMessage` as the hooks-browser title (0.162.0), managed Git worktree create/list tools "when the worktrees feature is on" (0.162.0, #50148), a "configurable default plugin activation policy" with no documented key (0.163.0, #52220), parallel read-only skill lookups (0.163.0, #52245), and two retirements: `approval_policy = "untrusted"` now "can stop either client from starting", and 0.163.0 emits a migration notice for configs using retired shell flags ([Sandbox & approvals](https://learn.chatgpt.com/docs/agent-approvals-security); [0.163.0](https://github.com/openai/codex/releases/tag/rust-v0.163.0)). The plugin's `.codex/config.toml` and `platforms/codex/` templates must be grepped for `untrusted` before V5.

The audit's headline is the one the maintainer asked to have flagged. Codex loads a plugin's `hooks/hooks.json` natively and sets `PLUGIN_ROOT`, `PLUGIN_DATA`, `CLAUDE_PLUGIN_ROOT` and `CLAUDE_PLUGIN_DATA` "for compatibility with existing plugin hooks" — but its `HooksFile` struct is `#[serde(deny_unknown_fields)]` with exactly two fields, `description` and `hooks`, so the top-level `modules` array this plugin added in 4.10.0 to the same file fails to parse ([hook_config.rs](https://raw.githubusercontent.com/openai/codex/main/codex-rs/config/src/hook_config.rs); [Hooks](https://learn.chatgpt.com/docs/hooks)). This is source-confirmed, not run live; whether the failure is a hard error or a warning that drops every hook is not established, but either way no plugin hook runs on Codex 0.163.0 today, which means `core/capabilities/platforms.json`'s `hooks: native` row for Codex is wrong in practice. The remedy the registry already names is correct: generate `platforms/codex/hooks.json` without `modules` and point `.codex-plugin/plugin.json` `hooks` at it, which "replaces default discovery rather than adding to it" ([Build plugins](https://developers.openai.com/plugins/build/plugins)). The generator should also drop the events Codex lacks (`Notification`, `DirectoryAdded`, `WorktreeCreate`, `WorktreeRemove`, `StopFailure`) rather than trusting `HookEventsToml` to ignore them, and it can add the Codex-only events the repo has handlers for: `PreCompact` already maps to `precompact-snapshot.sh`, and `SubagentStart`, `PostCompact`, `PermissionRequest` and `Interrupt` are new surfaces ([Hooks](https://learn.chatgpt.com/docs/hooks)). Two Codex-specific contract points need a test: `Stop` and `SubagentStop` hooks "must print JSON on exit 0, plain text is invalid", so `hooks/check-done.sh` and `hooks/subagent-handoff-check.sh` must emit JSON on Codex; and `PreToolUse` `"ask"`, `continue: false` and `stopReason` "are unsupported and fail the hook" ([Hooks](https://learn.chatgpt.com/docs/hooks)). `apply_patch` matching `Edit` and `Write` is what keeps `enforce-worktree-edits.sh`'s matcher working; `tests/hooks/test-apply-patch-*.sh` already cover the payloads.

Distribution is a second hard constraint: "Plugins with hooks aren't eligible for the public directory", hooks are "Supported for manually installed Codex desktop plugins only", local stdio MCP in the directory is "limited to approved partners", and the Codex IDE extension "doesn't support plugins" ([Build plugins](https://developers.openai.com/plugins/build/plugins); [Desktop-only](https://developers.openai.com/plugins/deploy/desktop-only); [Plugins](https://learn.chatgpt.com/docs/plugins)). The self-hosted route the repo already uses — `.agents/plugins/marketplace.json`, `codex plugin marketplace add Tamircohen28/tamirs-marketplace`, then `/plugins` — is the only one; note the `codex plugin install <name>` command recorded in `platforms.json` "was not confirmed on any fetched docs page". If a hookless Codex-directory listing is ever wanted, V5's build system should emit it the way `build-claude-dist.sh` emits the Claude subset, populating `extensions.com.openai.interface` and an `onboardingSkill` that mirrors the `SessionStart` bootstrap on a host where hooks cannot run ([Build plugins](https://developers.openai.com/plugins/build/plugins)). Also worth knowing: "Enabling a plugin does not trust its hooks" — users review them in `/hooks`, trust is tied to a hash, and a changed hook is skipped until re-trusted, so every V5 hook edit silently disables that hook on Codex until the user re-approves; the install doc must say so ([Hooks](https://learn.chatgpt.com/docs/hooks)).

The remaining component gaps are unchanged but now better characterised. Agents: the manifest parser accepts `name`, `version`, `description`, `keywords`, `skills`, `mcpServers`, `apps`, `hooks`, `interface`, `extensions` and a `commands` struct — no `agents` field — so the ten `agents/*.md` still have no plugin route; custom agents are standalone TOML in `~/.codex/agents/` or `.codex/agents/` with `name`, `description`, `developer_instructions`, `model`, `model_reasoning_effort` and `features.*` reductions, and subagent workflows are "enable[d] by default" with `spawn_agent`/`close_agent` tools ([manifest.rs](https://raw.githubusercontent.com/openai/codex/main/codex-rs/core-plugins/src/manifest.rs); [Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents)). A `scripts/build-codex-agents.sh` → `.codex/agents/*.toml` generator would give repo-level (not plugin-level) parity for projects that adopt the toolkit, and the Codex `subagents` row can be re-measured from `unknown` with one live run. Skills: Codex reads only `name`, `description` and `metadata.short-description` and silently ignores every other key, so `allowed-tools`, `user-invocable` and `disable-model-invocation` are no-ops; the Codex analogue of `disable-model-invocation: true` is a sibling `agents/openai.yaml` with `policy.allow_implicit_invocation: false`, and there is no analogue for hiding a skill from the user — the three internal companions are user-visible on Codex ([parser.rs](https://raw.githubusercontent.com/openai/codex/main/codex-rs/skills/src/parser.rs); [Build skills](https://learn.chatgpt.com/docs/build-skills)). MCP: `"mcpServers": "./.mcp.json"` is the documented compatibility form, but `${user_config.github_token}` is a Claude mechanism; whether Codex expands anything other than `${PLUGIN_ROOT}` is undocumented, so on Codex the token env is probably the literal string and the server refuses to start — the fix is a generated Codex `mcp.json` using `env_vars` or documented user config ([MCP](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)). Project instructions: Codex reads `AGENTS.md` layered root→cwd with a 32 KiB cap and never `CLAUDE.md` unless listed in `project_doc_fallback_filenames` ([AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md)). And a Codex plugin cannot ship a notification command (`notify` is user config), so the Pushover path has no Codex equivalent ([Config reference](https://learn.chatgpt.com/docs/config-file/config-reference)).

## Gemini CLI is in consumer sunset; Antigravity is the successor target

Every geminicli.com page now banners that "Gemini CLI was replaced by Antigravity CLI on June 18th, 2026" for unpaid and Google One users, and Google's post states that on that date Gemini CLI and the Code Assist IDE extensions "will stop serving requests" for Google AI Pro/Ultra and free individual Code Assist users, while enterprise Standard/Enterprise licence holders and paid Gemini API / Agent Platform key users keep access ([Google Developers Blog](https://developers.googleblog.com/en/an-important-update-transitioning-gemini-cli-to-antigravity-cli/); [changelog](https://geminicli.com/docs/changelogs/)). The OSS repo nonetheless ships weekly stables — 0.60.0 (Sep 15) through 0.64.0 (Oct 13), plus 0.65.0-preview.0 ([Releases](https://github.com/google-gemini/gemini-cli/releases)) — and 0.60–0.64 were security-hardening releases: user consent prompts for "extension environment changes" and sanitised runtime-altering env vars (#28863), hardened extension-loader path resolution (#29169), RFC 9207 `iss` enforcement in MCP OAuth (#29117), refresh-token preservation (#29339), and autonomous plan execution in non-interactive mode (#29539) ([v0.60.0](https://github.com/google-gemini/gemini-cli/releases/tag/v0.60.0); [v0.63.0](https://github.com/google-gemini/gemini-cli/releases/tag/v0.63.0)). Nothing changed the on-disk extension format, so the audit question becomes "does the plugin use the format at all", and the answer is partly no: `gemini-extension.json` declares only the MCP server, skills are a flat symlink mirror, agents are generated, and **no hooks, commands or policies ship**.

Gemini has had command hooks since v0.24.0 (default-on from v0.26.0) with eleven events — `SessionStart`, `SessionEnd`, `BeforeAgent`, `AfterAgent`, `BeforeModel`, `AfterModel`, `BeforeToolSelection`, `BeforeTool`, `AfterTool`, `PreCompress`, `Notification` — packaged in an extension's `hooks/hooks.json` ("not defined in the `gemini-extension.json` manifest"), with `${extensionPath}`, Claude-style exit codes (0 parse JSON, 2 block), `CLAUDE_PROJECT_DIR` as a compatibility alias, and a hard rule that "stdout must contain only the final JSON object" or the CLI defaults to allow ([Hooks](https://geminicli.com/docs/hooks/); [Hooks reference](https://geminicli.com/docs/hooks/reference.md); [Extension reference](https://geminicli.com/docs/extensions/reference.md)). The mapping is clean enough to generate: `PreToolUse`→`BeforeTool` with a regex matcher on Gemini tool names (`write_file|replace|run_shell_command`), `PostToolUse`→`AfterTool`, `UserPromptSubmit`→`BeforeAgent`, `Stop`→`AfterAgent`, `PreCompact`→`PreCompress`, and `SessionStart`/`SessionEnd`/`Notification` by name. The unverified part is the `tool_input` shape for `write_file`/`replace`/`run_shell_command`, which `hooks/lib/write-targets.py` and `hooks/lib/platform-tools.sh` would have to learn; the repo's registry says the 4 translated events via `gemini hooks migrate --from-claude` are "seven tenths transcription", and no live Gemini binary exists in the nightly environment. Gemini also offers three hooks Claude lacks — `BeforeModel`, `AfterModel`, `BeforeToolSelection` — and an extension-shipped **policy engine**: `policies/*.toml` `[[rule]]` with `toolName`, `argsPattern`, `commandPrefix`/`commandRegex`, `decision` (`allow`|`deny`|`ask_user`), `priority`, `subagent`, where "Gemini CLI ignores any `allow` decisions or `yolo` mode configurations in extension policies" — a deny-only guard layer that could carry `protect-other-branches` (deny `run_shell_command` with `git push --force`) and the sensitive-file rules without a single hook ([Policy engine reference](https://geminicli.com/docs/reference/policy-engine.md); [Extension reference](https://geminicli.com/docs/extensions/reference.md)). The manifest's `settings` array (`name`, `description`, `envVar`, `sensitive: true` stored in the system keychain) is the `userConfig` analogue the plugin should use for `GITHUB_PERSONAL_ACCESS_TOKEN` instead of "user exports the env var", noting that 0.60.0's consent prompt will now fire on install for such a setting; `excludeTools` and `plan.directory` (with `GEMINI_PLANS_DIR` in hooks) are further untouched fields ([Extension reference](https://geminicli.com/docs/extensions/reference.md)). Subagents are `.md` files with `name`, `description`, `kind`, `tools`, `mcpServers`, `model`, `temperature`, `max_turns`, `timeout_mins`; "Subagents cannot call other subagents", no parallel primitive is documented, and the generated `.gemini/agents/*.md` already omit `model` — the `parallel_subagents: unsupported` row stands ([Subagents](https://geminicli.com/docs/core/subagents.md)). Two housekeeping items remain from the registry: the repo lacks the `gemini-cli-extension` GitHub topic (so `plugin_marketplace` is `partial`), and an extension installed from a bare git URL logs an `Invalid tool name` error per canonical `agents/*.md` on every invocation.

The strategic decision is Antigravity. Its CLI `agy` imports Gemini extensions with `agy plugin import gemini`, converting "legacy extensions into native plugins" and "legacy commands … to skills", moving skills to `~/.gemini/antigravity-cli/skills/` and `.agents/skills/`, moving MCP to `mcp_config.json` with `serverUrl`, keeping `GEMINI.md`/`AGENTS.md` unchanged, and reporting "agents: skipped (none detected)" in one documented import ([Antigravity migration guide](https://antigravity.google/docs/cli/gcli-migration)). The native format is a folder with a required `plugin.json` (`name` matching `^[a-zA-Z0-9-_]+$`, optional `description`, `additionalProperties: false`), optional `mcp_config.json`, `hooks.json`, `skills/<name>/SKILL.md`, `agents/<name>.md`, `rules/<name>.md`; workspace plugins live in `.agents/plugins/`, global in `~/.gemini/config/plugins/`; install is `agy plugin install <marketplace|repo URL|path>` ([Antigravity plugins](https://antigravity.google/docs/plugins/)). Google says skills, hooks, subagents and extensions carry over "at launch" without 1:1 parity; one vendor doc claims `agy` "loads hooks but does not fire them yet" — unverified against any Google source, and the official "Lifecycle hooks" page was not fetched. obra/superpowers removed Gemini CLI support in v6.1.0 "after Google ended the CLI", restored it in v6.2.0, and shipped a native Antigravity Marketplace manifest in v7.0.0 ([RELEASE-NOTES.md](https://raw.githubusercontent.com/obra/superpowers/main/RELEASE-NOTES.md)). The V5 plan is to keep `gemini_cli` as a supported surface for API-key and enterprise users, add `antigravity` as a seventh surface with its own `platforms/antigravity/` adapter generating `plugin.json` + `mcp_config.json` (+ `hooks.json` once firing is verified), and add `.agents/skills/` to the canonical layout so Gemini, Antigravity, Codex, Cursor, OpenCode and Copilot all discover one tree — noting that the Antigravity `plugin.json` schema is closed and the Agent Plugins `plugin.json` (`$schema` required) is also closed, so the two cannot be the same file.

## OpenCode 2 breaks the V1 plugin, deprecates the permission shape and opens a TUI mods analogue

OpenCode now has two product lines: `opencode.ai/docs` documents OpenCode 1 (`opencode-ai`, v1.19.x, GitHub Releases) and `opencode.ai/v2/docs` documents OpenCode 2 (`@opencode/cli`, the line this repo pins at 2.0.14), with the upstream repo moved to `anomalyco/opencode`; 2.0.14 (Sep 22) to 2.0.32 (Oct 16) is 18 releases, `latest` is **2.0.32** not the 2.0.30 the drift issue reports, and the v2 line publishes no GitHub Releases — the official changelog has prose only from 2.0.26 ([npm registry](https://registry.npmjs.org/@opencode%2Fcli); [changelog](https://opencode.ai/changelog)). Three findings in this window each invalidate a current artifact. First, the migration page states "V1 plugin implementations do not run in V2": V2 plugins are `Plugin.define({ id, setup(ctx) })` from `@opencode/plugin` (renamed from `@opencode-ai/plugin`), so `skills/toolkit/usage-capture/opencode-plugin.mjs` — a V1 hooks object — is dead code on every 2.x host and must be ported to `ctx.event.subscribe()` ([migrate-v1 plugins](https://opencode.ai/v2/docs/build/plugins/migrate-v1/)). Second, the published schema's `$defs.PermissionConfig` is now the **deprecated** V1 object whose 15 keys (`bash, doom_loop, edit, external_directory, glob, grep, list, lsp, question, read, skill, task, todowrite, webfetch, websearch`) `scripts/check-opencode-permission-keys.sh` pins; the V2 model is `permissions`, an ordered array of `{ action, resource, effect }` where `bash`→`shell`, `task`→`subagent`, `doom_loop` and `lsp` are "Not current V2 Core actions", `list`/`todowrite` are unlisted, "The last matching rule wins", and — a real weakening — `external_directory` is **allowed by default** in V2 where V1 asked ([config.json](https://opencode.ai/config.json); [Permissions](https://opencode.ai/v2/docs/permissions/); [migrate-v1](https://opencode.ai/v2/docs/migrate-v1/)). Because 2.0.30 published "a config schema that accepts both V1 and V2 shapes" (#55524), the `--refresh` drift check keeps passing while the canonical shape has moved; the generated `.opencode/agent/*.md` still work through documented auto-translation, but `.opencode/agents/` (plural) with `permissions:` rules and explicit `mode: subagent` (V2's default mode changed to `primary`) is the forward target, and the worktree invariant now needs an explicit `external_directory` → `ask`/`deny` rule. Third, `skills` config paths "are resolved from the active OpenCode working directory, not the config file", so the repo-relative `skills/creative`, … entries in `opencode.json` resolve nothing when `opencode` is started from a subdirectory — flagged inference, not live-tested; V2 also discovers `.agents/skills` and `.claude/skills` natively, honours `OPENCODE_DISABLE_CLAUDE_CODE[_SKILLS]` (2.0.30), and reads only `name`, `description`, `metadata.opencode/autoinvoke` and `disable-model-invocation` from frontmatter, with `license`/`compatibility` "accepted … but not interpreted" and no name regex enforced ([Skills](https://opencode.ai/v2/docs/skills/)).

The V2 plugin API is also the first credible route to the capabilities the registry marks `unsupported` on OpenCode. Server plugins get `ctx.permission.hook("evaluate")` (mutable `effect: allow|ask|deny` — the V1 `permission.ask` successor and a clean mirror of a `PreToolUse` deny), `ctx.tool.hook("execute.before")` (throw to block, mutable `input`), `ctx.shell.hook("create.before")` with the full `command` string (where a `tee`/`sed -i` write guard belongs), `ctx.session.hook("prompt"|"context"|"compaction")`, `ctx.permission.assert` (2.0.29), `ctx.worktree.transform` to replace the worktree strategy, `ctx.storage`, and `ctx.credential.activate` (2.0.28) ([Build plugins](https://opencode.ai/v2/docs/build/plugins); [promise/permission.ts](https://raw.githubusercontent.com/anomalyco/opencode/v2.0.30/packages/plugin/src/promise/permission.ts)). A `platforms/opencode/plugin/` V2 plugin implementing the three core guards would move `hooks` from `unsupported` to `adapter`; whether it may shell out to the existing `write-targets.py` is not documented (the plugin runs in the host's Node/Bun runtime, so it is plausible but unverified). The separate TUI API (`@opencode/plugin/tui`, Solid/OpenTUI peers) is OpenCode's analogue of Claude mods: slots `home.footer.status`/`prompt.footer.status` ("after OpenCode's health indicators and before the version") for a statusline, `session.panel`/`sidebar.content` for an objective pane, `ui.toast`, `ui.dialog`, `attention.notify`, and `keymap.layer` commands with `slash` names; `storage.store` persists across restarts and syncs across instances ([CLI plugins](https://opencode.ai/v2/docs/build/plugins/cli)). No documented rate-limit payload exists to drive a handoff band; `ctx.session.hook("http.response")` is the plausible but unverified source. Subagents: the built-in `subagent` tool takes `background: true` ("returns immediately and notifies the parent when the child finishes"), `experimental.subagent_depth` defaults to 1 so an orchestrator must be the primary agent, and whether several foreground calls in one turn run concurrently is still undocumented — `parallel_subagents` stays `unknown` until a live run ([Tools](https://opencode.ai/v2/docs/tools/)). Smaller V2 facts the adapters must absorb: commands use `subagent: true` (`subtask` deprecated alias) and no longer expand `@path`; "OpenCode V2 recognizes `AGENTS.md` only. It does not use `CLAUDE.md` as a fallback"; MCP lives under `mcp.servers.<name>` as `{ type: "local", command[], environment }` with `protocol: "2026-07-28"` available, and the plugin declares no server there today; `policies[]` is a deny-only admin layer; and 2.0.27 added built-in worktree tools plus `worktree.directory` config ([Instructions](https://opencode.ai/v2/docs/instructions/); [MCP servers](https://opencode.ai/v2/docs/mcp-servers); [Policies](https://opencode.ai/v2/docs/policies/)).

## Agent Plugins 1.0, signed releases and token budgets are the bar V5 must clear

Four standards crystallised in 2026 and the repo tracks one of them. **Agent Plugins 1.0** (published 2026-08-06; proposed by Vercel, built with AWS, Anysphere, GitHub, Microsoft and OpenAI; launch clients ChatGPT, Codex, Cursor, GitHub Copilot, Kiro, VS Code; Anthropic absent) defines a root `plugin.json` with required `$schema` (`https://agent-plugins.org/schemas/1.0.0/plugin.schema.json`) and `name` (1–64 chars, lowercase, digits, hyphens, periods), optional `version`/`description`/`homepage`/`repository`/`author`/`license`/`keywords`/`extensions`, a closed schema where unknown top-level fields "are reported and ignored", a `skills/` directory of immediate children following the Agent Skills spec, and `mcp.json` with `stdio` and `streamable-http` transports expanding `${PLUGIN_ROOT}`/`${PLUGIN_DATA}`; client-specific data goes under `extensions.<reverse-domain>` and client-specific files in a top-level directory named after the namespace; 1.1.0 is a working draft that still covers only skills and MCP — "commands, hooks, agents, rules, and LSP servers" remain outside ([agent-plugins-spec 1.0.0](https://github.com/agentplugins/agent-plugins-spec/blob/main/spec/1.0.0.md); [1.1.0](https://github.com/agentplugins/agent-plugins-spec/blob/main/spec/1.1.0.md)). The host behaviours make adoption low-regret: Codex reads `extensions.com.openai` and, when present, "it replaces the `.codex-plugin/plugin.json` overlay entirely" — the two are not merged; Cursor loads a root `plugin.json` but prefers `.cursor-plugin/plugin.json` when both exist; Copilot CLI detects Agent Plugins by `$schema`, prefers the root manifest over `.plugin/` and `.claude-plugin/`, reads `.claude/` dirs for agents/skills/commands, and aliases `CLAUDE_PLUGIN_ROOT`/`CLAUDE_PLUGIN_DATA` to `COPILOT_PLUGIN_ROOT`/`COPILOT_PLUGIN_DATA` ([Build plugins](https://developers.openai.com/plugins/build/plugins); [cursor.com/docs/plugins](https://cursor.com/docs/plugins); [Copilot CLI plugin reference](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-plugin-reference)). The transport-naming trap is real: the standard says `streamable-http`, Claude's `.mcp.json` says `http`, and neither validates in the other, so `.mcp.json` and `mcp.json` must be dual-written from one source. GitHub Copilot CLI, which reads `.claude-plugin/` manifests and `com.github.copilot/{agents,commands,rules,hooks/hooks.json}` and runs `copilot plugin marketplace add`, is the cheapest additional host V5 could add.

**AGENTS.md** is now a Linux Foundation project under the Agentic AI Foundation, "used by over 60k open-source projects" and listed for 23 tools; Claude Code reads it through the built-in `cc-plugin-agents-md` mod (every session except those that cannot read it, with a `userConfig` picker `claude-md-or-agents-md`/`claude-md-and-agents-md`/`managed-only`/`claude-md`) ([agents.md](https://agents.md/); [Mods overview](https://code.claude.com/docs/en/plugins/mods)). **MCP 2026-07-28** removed the `initialize` handshake and `Mcp-Session-Id`, added MRTR in place of server-initiated elicitation/sampling/roots, deprecated DCR for CIMD and Roots/Sampling/Logging with a 12-month window, requires `Mcp-Method`/`Mcp-Name` headers on Streamable HTTP, and is negotiated by default by Claude Code stdio (2.1.292), OpenCode (`protocol`), and Gemini's RFC 9207 enforcement ([blog.modelcontextprotocol.io](https://blog.modelcontextprotocol.io/posts/2026-07-28/)). The **Agent Skills spec** requires `name` to match the parent directory, limits `description` to 1,024 chars, lists `license`, `compatibility`, `metadata` (string→string) and experimental `allowed-tools` as the portable set, and ships `skills-ref validate`; every Claude-only field the repo uses (`effort`, `user-invocable`, `disable-model-invocation`, `context`, `agent`, `model`) is outside it, OpenCode namespaces host keys under `metadata` (`opencode/autoinvoke`), and 44 clients are listed ([agentskills.io/specification](https://agentskills.io/specification); [clients](https://agentskills.io/clients.md)).

The quality bar comes from peers and from Anthropic's own tooling. obra/superpowers (~300.7k stars) installs into 16 harnesses from one repo via per-platform manifest directories (`.agents/plugins`, `.antigravity-plugin`, `.claude-plugin`, `.codex-plugin`, `.cursor-plugin`, `.devin-plugin`, `.hermes-plugin`, `.kimi-plugin`, `.muse-plugin`, `.opencode`, `.pi/extensions`, root `gemini-extension.json`), builds a deterministic Codex package (`package-codex-plugin.sh`), bootstraps hook-less hosts through skill discovery, and runs a behavioural cross-CLI lab (Quorum) whose live evals stay out of public CI; its community critique is token burn, ceremony and, until recently, no published evals, and its v6.4.2 "leaner plans, ~¼ time, ~⅓ tokens" release answered it ([obra/superpowers](https://github.com/obra/superpowers); [superpowers-evals](https://github.com/prime-radiant-inc/superpowers-evals/); [HN 48739459](https://news.ycombinator.com/item?id=48739459)). `claude plugin eval` (GA 2.1.269) runs each case three times with and without the plugin, reports Δ, offers six graders including mock MCP servers with `.replay/` recordings, and takes `--threshold`, `--max-cost-usd`, `--json` and (2.1.299) `--disallow-tools`; `claude plugin details` prints "Projected token cost: Always-on ~N tok", and the official marketplace highlights a plugin's "Context cost" at ≥2,000 always-on tokens ([plugin-evals](https://code.claude.com/docs/en/plugin-evals); [plugins/measure](https://code.claude.com/docs/en/plugins/measure)). Security is the sharpest edge: Snyk's ToxicSkills scan found 36.82% of 3,984 skills had at least one issue and 76 confirmed malicious, 91% via prompt injection; a May 2026 paper shows metadata-only attacks evade classifiers "in 36.5% to 100% of cases"; and no agent platform signs skills or plugins — the directory pins commits and verifies `archive` sha256, Copilot and Codex pin `sha`, but Sigstore/attestations appear only in proposals ([Snyk ToxicSkills](https://snyk.io/blog/toxicskills-malicious-ai-agent-skills-clawhub/); [arXiv 2605.14460](https://arxiv.org/pdf/2605.14460); [plugins/security](https://code.claude.com/docs/en/plugins/security)). The white space the landscape note identifies — a one-source N-target build with per-host conformance, signed releases, cross-host hook conformance tests, an always-on token budget gate, a portable handoff protocol and a published capabilities matrix — is mostly "finish and publish what this repo already half-has".

## Conclusion

The research reframes V5 from "catch up with five changelogs" to "stop hand-synchronising five formats". Every platform the plugin ships to has, in the last quarter, either converged on a Claude-shaped hook interchange (`CLAUDE_PLUGIN_ROOT`/`CLAUDE_PLUGIN_DATA` aliases on Codex, Cursor and Copilot; exit-code-2 blocking everywhere) or published a closed, generatable manifest (Agent Plugins 1.0, Antigravity `plugin.json`, OpenCode V2 schema) — and in each case the repo's current artifact is either missing, hand-maintained, or quietly broken by a parser the research could read but not run. The right investment is therefore a build system with per-target conformance checks and live-binary CI, not another round of prose notes; the mod work rides on top of that, and the guard/notify/contrib split is what lets the core keep a clean directory footprint while the ambitious in-process features ship to users who ask for them.

Two implications go beyond the plan. First, the field's measured criticism of agent plugins — token burn, ceremony, "snake oil" skills without evals — means V5's credibility rests less on feature count than on three published numbers: an always-on token figure under the 2,000-token marketplace highlight, a Δ score per skill, and a signed, verifiable release. No peer publishes all three. Second, the repo's honest capability registry, with its `unknown`-means-`unsupported` rule and 90-day evidence budget, is already the most rigorous artifact of its kind the research found; publishing it as a versioned release asset, and moving `validated_against` with real binaries in CI, turns an internal discipline into the plugin's most defensible claim to being industry-leading.
