# OpenCode CLI extensibility surface as of 2026-10-17 (v2 line, 2.0.14 → 2.0.32)

Scope note for the writer: OpenCode now has **two parallel product lines with two doc sites**. `https://opencode.ai/docs/*` documents **OpenCode 1** (v1.19.x, package `opencode-ai`, repo releases on GitHub); `https://opencode.ai/v2/docs/*` documents **OpenCode 2** (package `@opencode/cli`, the line this repo pins at 2.0.14). Several things this repo's `platform-targets.json`/`check-opencode-permission-keys.sh` currently cite (the 15-key `PermissionConfig`, `@opencode-ai/plugin` hooks like `tool.execute.before`, `permission.ask`, `chat.message`) are **V1 concepts that V2 keeps only as deprecated/compat shapes**. Every finding below says which line it belongs to. "Latest" was 2.0.32, not 2.0.30, on the research date.

Upstream repo moved: npm `@opencode/cli` `repository.url` is `git+https://github.com/anomalyco/opencode.git` (not `sst/opencode`) — [npm registry](https://registry.npmjs.org/@opencode%2Fcli).

## Key question 1 — What shipped between 2.0.14 and 2.0.30, and which items matter to a plugin author?

### Takeaway
2.0.14 (2026-09-22) → 2.0.30 (2026-10-15) is 16 releases in 23 days (plus 2.0.31/2.0.32 on 2026-10-16). The v2 line publishes **no GitHub Releases**; `https://opencode.ai/changelog` has prose only from v2.0.26 onward, so 2.0.15–2.0.25 had to be reconstructed from git tag commit subjects. The plugin-author-relevant changes are: the published config schema now accepts both V1 and V2 shapes (2.0.30), top-level `policies` stabilised (2.0.29), plugins can `ctx.permission.assert` (2.0.29) and `ctx.credential.activate` (2.0.28), `OPENCODE_DISABLE_CLAUDE_CODE[_SKILLS]` honoured (2.0.30), `instructions` globs/URLs load and refresh (2.0.30), session sharing backend and `/share` removed (2.0.30), built-in worktree tools (2.0.27), per-project auto-accept permissions (2.0.28), and the plugin runtime now shares the host's `effect` instance (2.0.25).

### Inferences
- For this repo's `platform-targets.json`, `reviewed_through` can advance to 2.0.32 on changelog+commit evidence; `validated_against` must stay 2.0.14 (no live binary run here).

## Key question 2 — Which plugin hook events exist today, with payloads, and which can block or modify?

### Takeaway
V2 replaces the V1 flat hooks object with `Plugin.define({ id, setup(ctx) })` from **`@opencode/plugin`** (renamed from `@opencode-ai/plugin`). "V1 plugin implementations do not run in V2." The V2 surface is split into **transforms** (synchronous editors on domains: provider, model, agent, command, skill, mcp, integration, reference, websearch, vcs, worktree, tool) and **hooks** (`session.hook`, `permission.hook`, `shell.hook`, `tool.hook`, model/http/ws/retry) whose payloads have mutable fields; blocking is done by throwing (tools) or by setting `effect`/`result`. There is also a separate TUI plugin API (`@opencode/plugin/tui`) that owns slots, dialogs, commands, keybindings, routes, panels and storage.

### Cited Findings

**Package, entrypoints, loading (V2)**

**Hooks (`Hooks<Spec> = (name, callback(input)) => Promise<Registration>`; ordered by registration; later hooks see earlier changes)** — [registration.ts](https://raw.githubusercontent.com/anomalyco/opencode/v2.0.30/packages/plugin/src/promise/registration.ts):
- `ctx.tool.hook("execute.before", e)`: `{ tool: string (mutable), sessionID, agent, messageID, id: Tool.CallID, input: unknown (mutable) }` — can replace `input`. `ctx.tool.hook("execute.after", e)`: readonly `tool/sessionID/agent/messageID/id/input` + either `{ status: "completed", result (mutable) }` or `{ status: "error", error }` — [promise/tool.ts](https://raw.githubusercontent.com/anomalyco/opencode/v2.0.30/packages/plugin/src/promise/tool.ts). Docs: `execute.before` "inspects or replaces `input`"; `execute.after` on completed "can change `result`"; Promise hook rejections are attached to their own tool call since 2.0.29 (`fix(plugin): keep each Promise hook rejection on its own tool call (#55263)`).
- `ctx.permission.hook("evaluate", e)`: `PermissionEvaluation { sessionID, agent?, action, resources, metadata?, source?, effect (mutable: allow|ask|deny), message? (mutable) }`; "Runs for `allow` and `ask`, not for explicit configured `deny`" — [permission.ts](https://raw.githubusercontent.com/anomalyco/opencode/v2.0.30/packages/plugin/src/promise/permission.ts), docs. This is the V1 `permission.ask` successor and **can block** by setting `effect = "deny"`.
- `ctx.permission.assert({ sessionID, agent?, source?, action, resources, save?, metadata? })`: "Evaluates the session's permission rules and, when approval is required, prompts the user and waits for the reply. Resolves when allowed. A deny rule or a rejection with feedback rejects with a `Tool.Error`" — source; added 2.0.29 (`#54930`).
- `ctx.session.hook("prompt", e)`: `SessionPrompt { sessionID, messageID (readonly), prompt (mutable DeepMutable<Prompt>), metadata?, delivery ("steer"|"queue") }`; docs: "runs once per admission, not for synthetic, shell, compaction, or move messages. It has no typed rejection API" — [session.ts](https://raw.githubusercontent.com/anomalyco/opencode/v2.0.30/packages/plugin/src/promise/session.ts), docs. (V1 `chat.message` successor; modify-only, cannot reject.)
- `ctx.session.hook("context", e)`: `SessionContext { sessionID, model, agent, system[], messages[], options, tools: Record<name,{description,input}> }` — modify `system`, `messages`, `tools` (delete entries), `options`; "Changes apply only to the outgoing call, not stored history". `"compaction"`: same + `result?: { summary, providerState?, metadata?, tokens? }` ("Set to use this compaction and skip the model request"). `"generate"` same as context. `"title"`: `SessionTitle { result?: string }`. `"model.request"`: `{ sessionID, agent, model, kind: "primary"|"compaction"|"title"|"generate", baseURL?, headers }` (optionally scoped by `providerID`). `"http.request"` (`request: Request` mutable) / `"http.response"` (`response` mutable). Experimental `"experimental.ws.handshake"` (`url`, `headers`), `"experimental.ws.send"`/`"experimental.ws.receive"` (`frame` string). `"retry"`: `{ error, attempt, decision: {retry:false}|{retry:true, delay} }` — source + docs.
- `ctx.shell.hook("create.before", e)`: `{ command, cwd, timeout, shell, env }` all mutable — [shell.ts](https://raw.githubusercontent.com/anomalyco/opencode/v2.0.30/packages/plugin/src/promise/shell.ts). (V1 `shell.env` successor; can rewrite the command.)
- `ctx.event.subscribe({ signal })`: async iterable of public events, read-only — [event.ts](https://raw.githubusercontent.com/anomalyco/opencode/v2.0.30/packages/plugin/src/promise/event.ts), docs.
- Session API on ctx: `create, get, remove, context, switchAgent, switchModel, update, move, prompt, generate, command, compact, synthetic, interrupt, wait`; `ctx.generate.text`; `ctx.credential.activate`; `ctx.integration.connect.key`, `oauth.*`; `ctx.worktree` (`create, list, refresh, remove`); `ctx.vcs` (`get, branches, status, diff`) — docs.

**V1→V2 hook mapping (official)** — [migrate-v1 plugins](https://opencode.ai/v2/docs/build/plugins/migrate-v1/): `event`→`ctx.event.subscribe()`; `config`→domain transforms; `auth`→`ctx.integration.transform`; `provider`→`ctx.provider.transform`/`ctx.model.transform`; `chat.message`→`ctx.session.hook("prompt")`; `chat.params`→`session.hook("context")` editing `options`; `chat.headers`→`"model.request"`/`"http.request"`; `permission.ask`→`ctx.permission.hook("evaluate")`; `command.execute.before`→command transform or prompt hook ("no one-to-one global hook"); `tool.execute.before/after`→`ctx.tool.hook(...)`; `shell.env`→`ctx.shell.hook("create.before")`; `tool.definition`/`tool` map→`ctx.tool.transform`; `experimental.chat.system.transform`/`messages.transform`→`"context"`; `experimental.session.compacting`→`"compaction"`; no equivalent for `experimental.compaction.autocontinue`, `experimental.provider.small_model`, `experimental.text.complete`.

### Inferences
- This repo's observe-only `skills/toolkit/usage-capture/opencode-plugin.mjs` is a V1-shape plugin (hooks object). Per the migration page it "does not run" on V2 unless ported to `Plugin.define` + `ctx.event.subscribe()`.
- A Claude-Code-style PreToolUse guard (worktree enforcement, sensitive-file guard) maps cleanly to `ctx.tool.hook("execute.before")` (throw to block) or, more idiomatically, `ctx.permission.hook("evaluate")` setting `effect: "deny"`. A `tee`-style Bash write guard maps to `ctx.shell.hook("create.before")` with access to the full `command` string.
- The TUI plugin API is OpenCode's analogue of Claude Code mods (statusline-like `home.footer.status`/`prompt.footer.status` slots, panels, toasts, keybindings). It is separate from the server plugin and requires Solid/OpenTUI peers.

### Gaps
- Exact `Tool.Info` input/output schema types (JSON Schema vs Effect Schema) and the full public event list for V2 (`V2EventEncoded` in the API reference) were not enumerated; the API page at `/v2/docs/api/` was not fetched (too large).
- Whether V2 logs an error or silently skips a V1-shaped plugin is not stated in the docs.

## Key question 3 — Does OpenCode support parallel subagents / agent teams now? How?

### Takeaway
V2 has a built-in `subagent` tool with a `background: true` flag that "returns immediately and notifies the parent when the child finishes", child sessions with their own permissions, and `experimental.subagent_depth` (default 1, so subagents cannot nest). There is **no "agent teams" feature**; parallelism is achieved by launching several background subagents (or via Code Mode `execute` for parallel independent tool calls). Whether multiple foreground `subagent` calls in one turn run concurrently is still not documented.

### Cited Findings
- `subagent` tool: "an agent ID, a short `description`, and a complete `prompt`. Also `background` (boolean) and a returned `sessionID` used to continue the same child conversation. Only subagent-mode agents qualify; default nesting depth is one. Permission: `subagent`"; "Foreground calls wait for the result"; "`background: true` returns immediately and notifies the parent when the child finishes" — [v2 docs tools](https://opencode.ai/v2/docs/tools/).
- `execute` (Code Mode) "is useful for 'parallel independent calls,' with an example that reads two files at once"; Code Mode runtime "has no direct filesystem access, imports, or timers. It provides `fetch`"; Code Mode namespaces include `opencode.worktree_create/list/remove`, `opencode.session_rename/move`, `browser` — same page.
- Agents page: "Subagents run with fresh context in foreground or background child sessions. The parent's `subagent` permission rules control which agents it can launch. The child uses its own configured permissions"; built-in `general` "Cannot launch more subagents"; hidden maintenance agents `compaction`, `title`, `summary` — [v2 docs agents](https://opencode.ai/v2/docs/agents/).
- `subagent_depth` top-level is **deprecated** ("Maximum subagent nesting depth. Defaults to 1, which prevents subagents from launching subagents"); V2 location is `experimental.subagent_depth` (integer ≥ 0) — [opencode.ai/config.json](https://opencode.ai/config.json), [migrate-v1](https://opencode.ai/v2/docs/migrate-v1/).
- Commands: "Delegated commands now run in the background and report results to the parent session"; command frontmatter `subagent: true` "runs in a background child session" — [migrate-v1](https://opencode.ai/v2/docs/migrate-v1/), [v2 docs commands](https://opencode.ai/v2/docs/commands).
- Desktop app shows "running subagents and shells in the session header" since 2.0.23 (`#53247`); `fix(cli): answer subagent asks in run and keep parallel rejections continuing (#52146)` in 2.0.20 — commit subjects (git tags).
- V1 history: issue #29638 (filed on v1.15.11) reported only one subagent running at a time with `background` hidden behind `experimentalBackgroundSubagents` — [anomalyco/opencode#29638](https://github.com/anomalyco/opencode/issues/29638) (via search summary; the repo's `platforms.json` records it was closed not-planned).
- TUI child-session navigation keybinds (V1 doc, also applies to v2 TUI per cli.json keybinds): `session_child_first`, `session_child_cycle`, `session_child_cycle_reverse`, `session_parent` — [v1 docs agents](https://opencode.ai/docs/agents/).
- Secondary coverage of the 2.0 announcement describes "asynchronous subagents" and that "code reviews, tests, and other independent tasks no longer need to block the primary agent's conversation" — [aiidelist.com](https://aiidelist.com/blog/opencode-2-0-release-code-mode-background-agents) (secondary).

### Inferences
- For `orchestrate-dev`/`worker-dev` fan-out: the honest mapping is `subagent` with `background: true` per worker, then collect results via parent notifications/`sessionID`; this is documented behaviour since v2 (the repo's `platforms.json` note that "the v2 tools docs document `background: true`" is confirmed). The "foreground calls in one turn run serially" concern from v1 is not contradicted by any v2 doc.
- `subagent_depth` default 1 means an orchestrator agent cannot itself be a subagent that spawns workers; the orchestrator must be the primary agent.

### Gaps
- No primary source states whether several foreground `subagent` calls issued in one assistant turn execute concurrently on v2.
- No live run; the `#52146` subject implies parallel subagent permission asks exist in `opencode run`, but the semantics are inferred from a commit title.

## Key question 4 — Which SKILL.md frontmatter fields does OpenCode honour?

### Takeaway
V2 honours `name` (display label, defaults to path-derived ID), `description` (required for the skill to be advertised), `metadata.opencode/autoinvoke` (`false` hides from `<available_skills>`), and `disable-model-invocation: true` (same effect; `opencode/autoinvoke` wins if both set); `license` and `compatibility` are "accepted in V2 but not interpreted". V2 does **not** enforce the V1 name regex/length rules, discovers `.claude/skills` and `.agents/skills` (project + global), supports HTTP catalogs, and lets users load a skill with `@skill-id`. `allowed-tools` is not mentioned anywhere.

### Cited Findings
- V2 frontmatter: "`name`: display label. Defaults to the path-derived ID. `description`: summary shown to the model. Skills without one are not advertised. `metadata.opencode/autoinvoke`: set to `false` to hide the skill from the model's available list. It stays loadable by ID. `disable-model-invocation`: `true` has the same effect. If both are set, `opencode/autoinvoke` wins. `license` and `compatibility`: accepted in V2 but not interpreted" — [v2 docs skills](https://opencode.ai/v2/docs/skills/).
- V2 does not enforce `^[a-z0-9]+(-[a-z0-9]+)*$`, the 1–64 char limit, name-to-directory matching, or max description length; "a root-level `SKILL.md` gets the literal ID `SKILL`"; "Markdown skills must sit at the source root (e.g., `skills/review.md`). Files named exactly `SKILL.md` can be at any depth" — same page.
- Discovery (V2): global `~/.config/opencode/skills`, `~/.claude/skills`, `~/.agents/skills`; project `.opencode/skills`, `.claude/skills`, `.agents/skills`, searched "from the current directory up to the project root"; precedence lowest→highest: built-in, `.claude/skills`, `.agents/skills`, `~/.config/opencode/skills`, project `.opencode/skills`, explicit `skills` config entries — same page.
- `skills` config: a flat array in any `opencode.json(c)`; entries are relative paths ("resolved from the active OpenCode working directory, not the config file"), `~/` paths, absolute paths, `http://`/`https://` URLs (HTTP catalogs needing `index.json`, files at `<base-url>/<name>/<file>`, bump `version` to refresh); "Arrays from every discovered config file are combined, not replaced" — same page. Schema: `skills` is `anyOf` string-array (current) or deprecated object `{ paths: string[], urls: string[] }` — [opencode.ai/config.json](https://opencode.ai/config.json).
- `skill` tool: input is the exact ID (`{"id": "git-release"}`); checks the agent's `skill` permission; "adds the Markdown body (without frontmatter) to the conversation, plus the skill's base directory and up to ten supporting file paths"; "Users can load a skill directly by mentioning `@skill-id` in a prompt" — same page.
- Permissions: rules in the `permissions` array with `"action": "skill"` and the skill ID as `resource`; per-agent under `agents.<id>.permissions` — same page. Policies can block a skill: `integration.use` with resource `skill:<id>` ("A denied MCP server or skill is removed") — [v2 docs policies](https://opencode.ai/v2/docs/policies/).
- `OPENCODE_DISABLE_CLAUDE_CODE` and `OPENCODE_DISABLE_CLAUDE_CODE_SKILLS` "are honored for `.claude` skills" since 2.0.30 — [changelog](https://opencode.ai/changelog); commit `fix(core): honor OPENCODE_DISABLE_CLAUDE_CODE (#55774)`.
- V1 (OpenCode 1) for contrast: `name` (required, regex, must match dir), `description` (1–1024), `license`, `compatibility`, `metadata` (string map) with recognised `opencode/slash` (`"true"` exposes `/name`) and `opencode/autoinvoke`; `permission.skill` pattern map; `tools.skill: false` disables — [v1 docs skills](https://opencode.ai/docs/skills/).
- Migration: skill dirs `skill/` and `skills/` both read; "Move the complete skill directory… keep the directory name stable so the skill ID is preserved" — [migrate-v1](https://opencode.ai/v2/docs/migrate-v1/).
- Repo's prior finding (platforms.json): symlinks not followed for skill discovery (verified 1.18.11) — not re-verified on v2 here.

### Inferences
- This repo's `opencode.json` `skills` array uses repo-relative paths (`skills/creative`, …). Under the V2 rule they resolve from the **working directory**, so running `opencode` from a subdirectory of the repo would resolve nothing — worth a note in `docs/user/install/opencode.md` (flagged inference; not live-tested).
- The `opencode/slash` metadata key is documented only on the V1 page; its V2 status is unknown (gap).
- `allowed-tools` (Claude Code) and `effort:`/`user-invocable`/`context: fork`/`agent:` (Claude Code) are ignored by OpenCode; the only OpenCode-honoured gating field is `disable-model-invocation`/`opencode/autoinvoke`.

### Gaps
- `opencode/slash` on V2: not documented; unknown whether skills can be exposed as slash commands in V2 (commands page says "Skills as slash commands: not covered").
- Symlink following on v2: not re-verified.

## Key question 5 — Which permission keys exist today (exact list)?

### Takeaway
There are now **two** permission models in one published schema. The V1 object `permission` (deprecated in V2) has exactly the 15 `PermissionConfig` keys this repo pins: `bash, doom_loop, edit, external_directory, glob, grep, list, lsp, question, read, skill, task, todowrite, webfetch, websearch` (plus `additionalProperties` for MCP `server_tool` names). The V2 model is `permissions`: an **ordered array** of `{ action, resource, effect }` where actions are `read, edit, glob, grep, shell, subagent, skill, question, webfetch, websearch, external_directory, execute, <server>_<tool>, opencode_list_mcp_resources, opencode_read_mcp_resource`; `doom_loop` and `lsp` are "Not current V2 Core actions"; `bash`→`shell`, `task`→`subagent`. Since 2.0.30 the schema at `https://opencode.ai/config.json` accepts both shapes and V2 auto-translates legacy agent frontmatter.

### Cited Findings
- Published schema (downloaded 2026-10-17): `$defs.PermissionConfig` = `anyOf [PermissionActionConfig, { properties: read, edit, glob, grep, list, bash, task, external_directory, todowrite, question, webfetch, websearch, lsp, doom_loop, skill; additionalProperties: PermissionRuleConfig }]`; top-level `permission` is `deprecated: true`; top-level `permissions` is `Permission.Ruleset` = array of `Permission.Rule { action: string, resource: string, effect: "allow"|"deny"|"ask" }`; `AgentConfig.permission` (V1) vs `Config.AgentEncoded.permissions` (V2 ruleset) — [opencode.ai/config.json](https://opencode.ai/config.json). The 2.0.30 commit: `fix(schema): publish config schema that accepts V1 and V2 shapes (#55524)`.
- V2 actions and resources: `read` (location-relative internal path or canonical absolute external path), `edit` (target path for `edit`, `write`, `patch`), `glob` (pattern), `grep` (regex, not the search path), `shell` ("scanner-produced command string; compound commands may yield several"), `subagent` (target agent ID), `skill` (skill ID), `question` (`*`), `webfetch` (URL), `websearch` (query), `external_directory` ("canonical external directory boundary, normally ending in `/*`"), `<server>_<tool>` (MCP), `opencode_list_mcp_resources` (server name), `opencode_read_mcp_resource` (`<server>:<uri>`), `execute` (`*`; "A deny removes Code Mode and tools reachable only through it"); "Not current V2 Core actions: `doom_loop` and `lsp`"; "plugins may add more" — [v2 docs permissions](https://opencode.ai/v2/docs/permissions/).
- V2 evaluation: "No matching rule: defaults to `ask`"; "The last matching rule wins"; load order "lower-priority configuration first, then global rules, then agent rules"; multi-resource ops: "any `deny` denies, otherwise any `ask` asks, otherwise it's allowed"; pattern `*` (incl. `/`), `?`, whole-value match, Windows case-insensitive; "A shell pattern ending in ' *' also matches the bare command"; base defaults `*`/`*`→allow, `read *.env`→ask, `read *.env.*`→ask, `read *.env.example`→allow; **`external_directory` is allowed by default in V2** (V1 asked) — same page; [migrate-v1](https://opencode.ai/v2/docs/migrate-v1/).
- Shipped agent policies (V2): `build` allows questions; `plan` allows questions, denies edits except under `~/.opencode/plan`; `general` denies questions and subagent launches; `explore` denies everything except shell, read, glob, grep, webfetch, websearch, external directories; `title`/`summary` deny all; `compaction` base policy only — [v2 docs permissions](https://opencode.ai/v2/docs/permissions/).
- Approvals: `once`, `always` ("saves the tool's proposed patterns as project-scoped `allow` rules. These never override a `deny`"), `reject` ("rejects it and all other pending requests in that session") — same page. Per-project auto-accept permissions (`mod+shift+a`) since 2.0.28; `opencode --auto` / `opencode run --auto` auto-approves asks while "Explicit `deny` rules are still enforced" — [changelog](https://opencode.ai/changelog), [v1 docs permissions](https://opencode.ai/docs/permissions/).
- `experimental.portable_shell_scanner: true` replaces the tree-sitter shell scanner (no fallback) — [v2 docs permissions](https://opencode.ai/v2/docs/permissions/).
- Policies (separate layer, never prompt, only tighten): `policies[] { action: "provider.use"|"tool.use"|"integration.use", resource, effect: "allow"|"deny" }`; `tool.use` resource `<action>:<value>` e.g. `shell:git push *`, `edit:*.env`; `integration.use` resources `mcp:<server>`, `skill:<id>`, `plugin:<target>`; precedence reversed (Console > macOS managed prefs > system > global > project); "Earlier releases read policies from `experimental.policies`. That key still works" — [v2 docs policies](https://opencode.ai/v2/docs/policies/); stabilised in 2.0.29 (`feat(core): stabilize top-level policies config (#55297)`).
- V1 translation: "`bash` → `shell`; `task` → `subagent`; `write` and `patch` → `edit`"; agent frontmatter `permission`→`permissions`, "V2 translates legacy frontmatter automatically, so these edits are optional"; `tools` map folded into `permissions` as deny rules — [migrate-v1](https://opencode.ai/v2/docs/migrate-v1/).
- V1 (OpenCode 1) reference list for `permission` object keys: `read, edit, glob, grep, list, bash, task, external_directory, webfetch, websearch, lsp, skill, question, doom_loop` (+ `*`); V1 docs do not list `todowrite` though the schema does — [v1 docs permissions](https://opencode.ai/docs/permissions/), [v1 docs agents](https://opencode.ai/docs/agents/).

### Inferences
- `scripts/check-opencode-permission-keys.sh`'s pinned 15-key list still matches the **deprecated** `PermissionConfig`; `--refresh` therefore keeps passing while the canonical V2 shape has moved to `permissions[]` with `shell`/`subagent`. The generator currently emits `bash`/`task` (V1 names) in `permission:` maps, which V2 auto-translates — so the adapters still *work*, but the "emitted key must exist" guarantee should be re-pointed at the V2 action vocabulary (and `doom_loop`/`lsp`/`todowrite` dropped from any future V2 emission).
- Emitting `list: deny` is harmless but `list` is not a documented V2 action either (the V2 page lists no `list` action; `glob` covers listing) — flagged, not confirmed.
- The V2 default `external_directory: allow` is a weakening relative to V1 that matters for this repo's worktree invariant (`#182` item 9); adopting V2 would want an explicit `external_directory`→`ask`/`deny` rule.

### Gaps
- Whether `list` and `todowrite` are still recognised as V2 actions is not stated (neither listed as current nor as removed).
- No live confirmation of how the host behaves when a V1 `permission` map and a V2 `permissions` array are both present in one agent file ("Nested entries for agents… must each use one format").

## Key question 6 — What does OpenCode NOT support that Claude Code does (mods, statusline, output styles, userConfig)?

### Takeaway
OpenCode has no `hooks.json`, no shell-script hook events, no output styles, no plugin `userConfig`/credential prompts, no `.mcp.json`, no `CLAUDE.md` (V2 reads `AGENTS.md` only), no marketplace manifest, and no Claude-style statusline file. Its equivalents are: JS/TS server plugins (hooks/transforms), TUI plugins (slots incl. footer status, panels, toasts, keybindings), `plugins[].options` (plain JSON, not secret-typed), `ctx.credential.activate`/integration OAuth for secrets, `policies` for admin control, and `cli.json` for theme/keybinds.

### Cited Findings
- **Hooks**: OpenCode's only lifecycle mechanism is the plugin API (V2: `ctx.tool.hook`, `ctx.permission.hook`, `ctx.shell.hook`, `ctx.session.hook`) — [v2 docs build/plugins](https://opencode.ai/v2/docs/build/plugins). No `hooks.json` or shell-command hook format is documented on any v1 or v2 page (nav lists: [v1](https://opencode.ai/docs/), [v2](https://opencode.ai/v2/docs/)). Repo's `platforms.json` already records "OpenCode has no hooks.json".
- **Mods / statusline**: no "statusline" page exists in either nav; the TUI plugin API provides `home.footer.status` and `prompt.footer.status` slots ("Status items appear after OpenCode's health indicators and before the version"), `session.panel`, `sidebar.footer`, toasts, dialogs, `keymap.layer` commands with `slash` names — [v2 docs build/plugins/cli](https://opencode.ai/v2/docs/build/plugins/cli). Unlike Claude mods, these require Solid/OpenTUI peer deps and run only in the terminal client (CLI-only plugins "stay active when connected to a remote server" via `cli.json`).
- **Output styles**: no page or config key in v1/v2 navs or in the schema's top-level properties (`$schema, agents, commands, compaction, default_agent, enterprise, experimental, formatter, instructions, lsp, mcp, media, model, permissions, plugins, policies, providers, references, share, shell, skills, snapshots, tool_output, update, username, warming, watcher, websearch, worktree` + deprecated V1 keys) — [opencode.ai/config.json](https://opencode.ai/config.json). The nearest analogue is per-agent `system` (V2) replacing the provider base prompt — [v2 docs agents](https://opencode.ai/v2/docs/agents/).
- **userConfig**: plugin options are `{ "package", "options": { ... } }` → `ctx.options: Readonly<Record<string, any>>` (plain JSON in config, no sensitive-type prompting) — [options.ts](https://raw.githubusercontent.com/anomalyco/opencode/v2.0.30/packages/plugin/src/options.ts), [v2 docs plugins](https://opencode.ai/v2/docs/plugins/). Secrets: `{env:NAME}` and `{file:path}` substitution in config — [v2 docs config](https://opencode.ai/v2/docs/config); plugin-side `ctx.credential.activate` (2.0.28) and `ctx.integration.connect.key`/`oauth.*` — [v2 docs build/plugins](https://opencode.ai/v2/docs/build/plugins); `opencode auth export`/`import` (2.0.20 `#52139`).
- **Project instructions**: "OpenCode V2 recognizes `AGENTS.md` only. It does not use `CLAUDE.md` as a fallback"; global `~/.config/opencode/AGENTS.md`; nested `AGENTS.md` loads lazily when the agent reads under that dir; `instructions[]` accepts files, globs, `~/`, absolute, HTTP(S) URLs (5 s timeout) loaded after `AGENTS.md`; `OPENCODE_DISABLE_PROJECT_CONFIG=1` skips project discovery — [v2 docs instructions](https://opencode.ai/v2/docs/instructions/). (V1 did fall back to `CLAUDE.md`; migration page: "A `CLAUDE.md` fallback must be moved into `AGENTS.md`" — [migrate-v1](https://opencode.ai/v2/docs/migrate-v1/).)
- **MCP**: config lives under `mcp.servers.<name>` in `opencode.json(c)` ("V2 does not place server names directly under `mcp`"); no `.mcp.json` mention — [v2 docs mcp-servers](https://opencode.ai/v2/docs/mcp-servers).
- **Marketplace/registry**: no built-in registry; the Ecosystem page is a PR-maintained table (~39 plugins, 11 projects, 2 agents) pointing to awesome-opencode and opencode.cafe; many plugins use an `opencode-` npm prefix — [docs ecosystem](https://opencode.ai/docs/ecosystem/). Install is via `plugins[]`/`opencode plugin add` (npm or git) — [v2 docs plugins](https://opencode.ai/v2/docs/plugins/).
- **LSP**: "V2 preserves `lsp` config but does not run language servers, expose LSP tools, or produce diagnostics" — [migrate-v1](https://opencode.ai/v2/docs/migrate-v1/).
- **Session sharing**: schema `share: "manual"|"auto"|"disabled"` and `enterprise.url` remain, but "The retired session-sharing backend and `/share` were removed" in 2.0.30 — [changelog](https://opencode.ai/changelog); `refactor(tui): remove permanently disabled unshare command (#53003)` in 2.0.23.
- **Eval harness, `claude plugin validate`, plugin manifest fields (privacy/support URLs), `Monitor`/`Workflow` tools**: nothing equivalent appears in any v1/v2 nav page or the schema (absence inferred from the full nav lists above).

### Inferences
- A faithful OpenCode port of this plugin's safety hooks is only possible as a V2 server plugin (`Plugin.define`) registered via `plugins[]`; shell scripts in `hooks/` cannot be wired. A TUI plugin could reproduce the statusline (`home.footer.status`) and the rate-limit handoff band (`attention.notify` + `ui.toast`), but there is no documented rate-limit payload from the server comparable to Claude's `rate_limits`.
- `policies` (admin, deny-only) is the OpenCode analogue of Claude managed settings, not of hooks.

### Gaps
- No doc states whether a V2 server plugin can see model rate-limit/usage headers in `http.response` to drive a handoff band; plausible via `ctx.session.hook("http.response")` but unverified.

## Additional surface — Agents, commands, config, providers, TUI, server/SDK/apps, worktrees, console

### Takeaway

### Cited Findings
**Agents (V2)** — [v2 docs agents](https://opencode.ai/v2/docs/agents/), [migrate-v1](https://opencode.ai/v2/docs/migrate-v1/), [config.json](https://opencode.ai/config.json):

### Inferences
- The repo's generated `.opencode/agent/*.md` (singular dir, V1 `permission:` map with `bash`/`task`) remains loadable on V2 by the documented legacy translation, but the preferred V2 target is `.opencode/agents/` with `permissions:` rules and `mode: subagent` explicit (V2 default mode changed to `primary`, so any adapter omitting `mode` would become a primary agent). This repo's adapters set `mode` explicitly, so unaffected.
- `.opencode/commands/` generated files with `description/agent/model/subtask` are V2-compatible (`subtask` still accepted); switching to `subagent` is the forward-compatible edit.
