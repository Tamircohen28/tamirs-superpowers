# CLAUDE.md — tamirs-superpowers

Claude Code and Claude Desktop specifics for contributors. **Everything that is not Claude-specific lives elsewhere — start with [`AGENTS.md`](AGENTS.md)**, which is the shared entrypoint into [`core/`](core/) and [`rules/`](rules/README.md). This file adds only what is true of the Claude platform's two surfaces.

When this file and a canonical rule disagree, the canonical rule wins.

## What this repo is

A multi-platform agent plugin (skills, agents, hooks, MCP stubs) shipped to six supported surfaces across five platforms: Claude (Claude Code, Claude Desktop), Codex (Codex CLI), Cursor (Cursor IDE), Gemini (Gemini CLI), and OpenCode (OpenCode CLI). No build step, no `package.json`, no compiled output — Markdown, JSON, and Bash.

Claude Code and Claude Desktop are **one distribution**, not two formats: the same `.claude-plugin/plugin.json`, the same `skills/`, the same `agents/`. They are two **surfaces** of one platform: what differs is the runtime (installation path, no CLI flags, and the capability rows Desktop has never had measured), documented in [`docs/user/install/claude-desktop.md`](docs/user/install/claude-desktop.md).

## Claude-only capabilities

Do not assume these exist on other providers — check [`core/capabilities/platforms.json`](core/capabilities/platforms.json) before relying on any of them, and degrade explicitly per [`core/policies/safety.md`](core/policies/safety.md).

- **Subagents** (`Agent` tool) — parallel worker execution, measured on Claude Code; not exercised on Desktop. Other providers run tasks sequentially or through their own mechanism. Since **Claude Code 2.1.243**, `/tasks` and the agent detail dialogs also show which model and effort level each subagent ran on — useful for spot-checking `orchestrate-dev`/`worker-dev` fan-outs without instrumenting anything here. The same release fixed background subagents not waking when their last background Bash task finished; if a fanned-out worker previously seemed to hang after its shell command completed, that was a host bug, not this repo's orchestration. Since **Claude Code 2.1.246**, a subagent that stops because it hit its own `maxTurns` limit now returns its output marked `partial` with a hint to continue it via `SendMessage` — this repo's own handoff vocabulary (`completed`/`partial`/`failed`/`blocked`, see [`worker-dev`](skills/dev-workflow/worker-dev/SKILL.md)) already treats `partial` as "decide, never quietly integrate around it," so a `maxTurns`-truncated worker now surfaces the same way a worker that self-reports `partial` does — no orchestrator change needed, but worth knowing the label can now come from the host, not just from the worker's own handoff file. Since **Claude Code 2.1.247**, a subagent whose first model call 404s no longer dies outright — it now falls back through the session's own fallback model chain with a detailed error, the same reliability class of fix as the two above; a fanned-out `worker-dev` task that previously looked like a hard failure on a transient model-routing error may now simply continue on a fallback model instead. Since **Claude Code 2.1.251**, `CLAUDE_CODE_SUBAGENT_MODEL` sets only the *default* subagent model instead of overriding every spawn: an agent definition's own `model:` field (every `agents/*.md` here pins one explicitly, e.g. `model: sonnet`) and an explicit per-spawn model now take precedence over it. Before this fix, a user or CI environment exporting `CLAUDE_CODE_SUBAGENT_MODEL` could silently run every specialist agent on the wrong model regardless of its frontmatter pin; that can no longer happen. Since **Claude Code 2.1.257**, `CLAUDE_CODE_SUBAGENT_MODEL_FORCE` is the deliberate opposite: set it and every subagent runs on `CLAUDE_CODE_SUBAGENT_MODEL` (or the main model) regardless of an `agents/*.md` frontmatter `model:` pin or an explicit per-spawn model — the 2.1.251 guarantee above holds only when `_FORCE` is unset. Nothing in this repo sets it; it is documented here so a user or CI environment that does set it understands why a specialist agent is suddenly running on an unexpected model. Since **Claude Code 2.1.259**, two related bugs are fixed: auto mode no longer runs an unsupported model when an agent's frontmatter `model:` field names one, and interactive sessions no longer silently ignore that same field — both are exactly the `agents/*.md` `model:` pin this repo relies on (see the 2.1.251/2.1.257 notes above), so this closes latent unreliability in a mechanism already documented here rather than requiring any change to it. Since **Claude Code 2.1.265**, resuming a foreground-spawned subagent no longer rewrites its tool list or system prompt and no longer breaks prompt-cache reuse — a `worker-dev` task that gets resumed mid-fan-out previously risked a silent tool-surface drift or a full re-cache cost on resume; neither can happen now. The same release fixed agent teammates and resumed subagents moving `SubagentStart` hook context out of the prompt prefix — this repo does not currently wire a `SubagentStart` hook (`hooks/hooks.json` declares `SessionStart`, `SessionEnd`, `PreToolUse`, `PostToolUse`, `Stop`, `UserPromptSubmit`, `Notification`, `DirectoryAdded`, `WorktreeCreate` and `WorktreeRemove`, not `SubagentStart`), so the fix changes nothing here today but is worth knowing before anyone adds one. Also since **2.1.265**, a forked skill's kickoff prompt and text turns now stream as progress events instead of arriving silently — this repo ships exactly one forked skill, `targeted-debug` (`context: fork`, `agent: Explore`), so its fan-out is now visible turn-by-turn rather than looking idle until it returns.
- **Hooks** — `hooks/hooks.json` is loaded by Claude Code and the Codex CLI only — the Cursor IDE plugin does not wire it; Gemini CLI and OpenCode CLI have their own or none. Since **Claude Code 2.1.247**, hook and background-task error output that previously could overflow the conversation with a "Prompt is too long" error, or leak memory unboundedly on repeated output-file write failures, is fixed host-side — relevant here given the volume of hooks this plugin wires (25 scripts across `PreToolUse`/`PostToolUse`/`SessionStart`/`SessionEnd`/`UserPromptSubmit`/worktree events), though no hook here needed a change: none of them write to an unbounded log file themselves. Since **Claude Code 2.1.251**, `SessionStart` payloads for a resumed or forked session can also carry `seconds_since_last_response`/`context_tokens` (staleness) and `prompt_cache_likely_expired`/`estimated_cache_write_usd` (estimated re-cache cost); `hooks/session-init.sh` now adds a one-line `additionalContext` note when the resumed cache has likely expired, so that shows up before the first request re-caches rather than being inferred afterward from an unexplained cost/latency spike. The same release added `PreModelSwitch`/`PostModelSwitch` hook events (block, confirm, or annotate a model switch) — not wired here, since nothing in this repo's orchestration currently needs to gate or observe a model switch; noted for Tamir's judgment rather than wired speculatively. Since **Claude Code 2.1.259**, a blocking `Stop` hook no longer discards the turn's reasoning or forces a prompt-cache miss on the next turn — relevant given `hooks/check-done.sh`, `hooks/handoff-reminder.sh`, `hooks/release-agent-claims.sh` and `hooks/plugin-version-watch.sh` all run on `Stop`/`SessionEnd`, though none of them block by design (they inform; they never gate), so this removes a host-side cost/latency tax this repo was already avoiding rather than one it was paying. The same release also fixes worktree isolation refusing hook-created worktrees on some machines, and worktree-isolated sessions wrongly refusing Bash loops, `xargs` pipelines, and launcher-wrapped commands — `hooks/worktree-create.sh` creates every worktree here and `hooks/enforce-worktree-edits.sh` gates every `Edit`/`Write`/`MultiEdit`/`NotebookEdit` inside one, so both fixes land squarely on this repo's core-safety-invariant hooks; there was no repo-side workaround for either to remove, just fewer false-positive refusals going forward. Since **Claude Code 2.1.260**, `permissions.blockReadsOutsideWorkingDirectories` on macOS no longer hides the user's git config from sandboxed git, nor a worktree-isolated sub-agent's own checkout — this repo does not set that permission itself (it was reviewed and left out of `platforms/claude/settings.d/` in an earlier cycle as a personal auto-mode preference, not a plugin default), but the fix directly benefits worktree isolation for anyone who enables it alongside `hooks/worktree-create.sh`/`hooks/enforce-worktree-edits.sh`. Since **Claude Code 2.1.268**, `PermissionRequest` hooks now fire in `--print` (headless) mode — not exercised here, since `hooks/hooks.json` wires no `PermissionRequest` event — and `CLAUDE_CODE_SESSIONEND_HOOKS_TIMEOUT_MS` now actually extends a `SessionEnd` hook that declares no per-hook `timeout` of its own (previously still cancelled at 1.5 seconds regardless of the env var); every `SessionEnd` hook this repo ships (`session-end.sh`, `handoff-reminder.sh`, `release-agent-claims.sh`) already sets an explicit per-hook `timeout` in `hooks/hooks.json`, so this fix changes nothing here today, but matters before anyone adds a `SessionEnd` hook without one. The same release also fixed `/mcp`/`/plugin` server details, `claude mcp list`/`get`, and MCP login errors showing a secret resolved from a `${VAR}` placeholder in an MCP config — this repo's `.mcp.json` declares no `${VAR}` placeholder (the one server, `github`, resolves its token inside `scripts/github-mcp.sh` via `gh auth`, not through config-level substitution), so nothing here was ever exposed, but the fix protects any downstream fork that does use one. And a respawned in-process teammate no longer picks up tools or a system prompt from a same-named agent file in an untrusted folder — this repo's `agents/*.md` live inside the trusted, versioned plugin checkout, so not a scenario this repo's own orchestration creates, but relevant to anyone fanning out `orchestrate-dev`/`worker-dev` from a workspace that also contains untrusted agent definitions. Since **Claude Code 2.1.261**, resuming a session no longer loses hook output that was produced around parallel tool calls — relevant given the volume of hooks this plugin wires, though nothing here needed a workaround: no hook depended on output surviving a resume mid-parallel-call. The same release improved the host's dangerous-`rm` confirmation prompt to also catch `rm -rf` invoked on a positional parameter (e.g. `f="$1"; rm -rf "$f"`) rather than only a literal path — this is a built-in confirmation shown to the user before the tool call runs, independent of `PreToolUse` hooks, so it does not change what `hooks/enforce-worktree-edits.sh` or `hooks/guard-sensitive-files.sh` see; it is a second, host-side layer that now covers a shell pattern those hooks' PreToolUse matching does not specifically target.
- **MCP** — `.mcp.json` declares one stdio server (`github`, via `scripts/github-mcp.sh`). Since **Claude Code 2.1.265**, an MCP server declared `"type": "http"` with only legacy HTTP+SSE support now auto-falls-back to that transport instead of never connecting — this repo's own server is `stdio`, so the fix changes nothing here, but it is worth knowing before adding or recommending an `http`-type server in a downstream `.mcp.json`.
- **Statusline** — wired via `.claude-plugin/plugin.json` `settings.statusLine` → `scripts/statusline.sh`. Claude Code only — Desktop has no terminal chrome to render into. Test with piped JSON: `echo '<session-json>' | bash scripts/statusline.sh` — it blocks forever on unpiped stdin. Since **Claude Code 2.1.251**, the payload can also carry `rate_limits.spend_limit` (behind a Claude apps gateway with a spend limit configured); the statusline renders it as a fourth line using the exact same only-when-present pattern as the existing 7-day line, so nobody outside a gateway with a spend limit configured sees any change.
- **`EnterWorktree`** — automates worktree creation under `.claude/.worktrees/<name>`. That is the *legacy* layout; it stays supported and is never orphaned, but new objectives use `.agent-worktrees/<objective>/` per [`rules/dev/git-worktree-agent-workflow.md`](rules/dev/git-worktree-agent-workflow.md). `resolve-worktree.sh` understands both.
- **Project memory** — `.claude/memory/` (versioned backup, reviewable in PRs) mirrored into a per-project transcript directory (auto-loaded each session). Keep them in sync; commit new memory files to `.claude/memory/`. The transcript directory name is normally *derived* from the clone's absolute path (`-Users-<you>-Projects-tamirs-superpowers`), which shifts per machine/username and breaks if the clone moves. Since **Claude Code 2.1.234**, `CLAUDE_CODE_PROJECT_DIR_NAME` overrides that derivation — pin it (e.g. in `~/.zshrc`/`~/.bashrc`, or per-session) for a stable, machine-independent name:

  ```bash
  export CLAUDE_CODE_PROJECT_DIR_NAME=tamirs-superpowers
  ```

  Restoring memory on a new machine prefers the pin when set, falling back to the derived path
  otherwise — the fallback assumes the standard `~/Projects/tamirs-superpowers` clone location, so
  set the pin explicitly on any other layout (headless/Linux checkouts, a different parent
  directory, a different username than the one Claude derived from):

  ```bash
  MEMORY_DIR=~/.claude/projects/${CLAUDE_CODE_PROJECT_DIR_NAME:--Users-$(whoami)-Projects-tamirs-superpowers}/memory
  mkdir -p "$MEMORY_DIR" && cp .claude/memory/* "$MEMORY_DIR/"
  ```

## Claude Code CLI baseline

Root [`.claude-code-version`](.claude-code-version) is a machine-readable pin for the Claude Code **host CLI** version this repo's narrative docs are written against — not to be confused with `plugin-version.json`, which is this **plugin's own** release version and has nothing to do with which `claude` build a contributor or CI runner has installed. It exists because the two prose sources that track host-version-gated behavior — this file's "Claude-only capabilities" section and `core/capabilities/platforms.json`'s `since`/`notes` fields — never state a single current baseline in one machine-readable place; a script or a future review pass had to reverse-engineer "the highest version mentioned in prose" to find one.

The detailed, evidence-backed version of the same claim — `validated_against` (last live-CLI run) vs. `reviewed_through`/`latest_known` (changelog read, no live run required) as two distinct fields, plus the full per-release verification notes — lives in [`docs/engineering/build-and-release/platform-targets.json`](docs/engineering/build-and-release/platform-targets.json)'s `targets.claude_code` block; `.claude-code-version` is a thin, always-current mirror of that block's three version fields for a consumer that wants one file at a known root path rather than a JSON-path lookup. Treat `platform-targets.json` as authoritative on any disagreement and update `.claude-code-version` to match.

**This deliberately does not repeat the `.codex-version`/`.cursor-version` pattern uncritically.** Those two root files are documented as unread, hand-maintained drift risk (`docs/engineering/refactor/file-inventory.md` §2.3/§6.12: "read by no script at all," "orphan truth"). `.claude-code-version` is referenced here specifically so it is not silently orphaned the same way; no script parses it yet, which is the same gap those two have, and closing it — a small `scripts/check-platform-version-pins.sh`, or folding all three root pins into `check-platform-targets.sh` — is a reasonable follow-up rather than something this pass invents unasked.

## Marketplace cache

The installed copy lives under `~/.claude/plugins/cache/tamirs-marketplace/tamirs-superpowers/<version>/`. Claude uses the manifest `version` as the update cache key — pushing commits without a bump does not reach installed users. After a release:

```text
/plugin marketplace update tamirs-marketplace
/plugin update tamirs-superpowers@tamirs-marketplace
```

`/reload-plugins` reloads the **local cache** only; it never fetches from GitHub. For local development, symlink the cache directory at your clone or run with `--plugin-dir` — never hand-edit files under the cache. Full mechanics, including the version-glob failure mode: [`rules/dev/plugin-version-bump.md`](rules/dev/plugin-version-bump.md). Since **Claude Code 2.1.265**, `--plugin-dir` also accepts a **folder of plugins** — each child folder with a manifest loads, and the set hot-reloads while running. This repo ships a single plugin, so the existing single-plugin `--plugin-dir .` form still applies unchanged; the folder form only matters to a contributor who develops this plugin alongside another local plugin in a shared parent directory, in which case pointing `--plugin-dir` at that parent picks up both. Since **Claude Code 2.1.268**, installing, enabling or disabling a plugin through the **interactive `/plugin` menu** takes effect as soon as the menu closes — `/reload-plugins` is no longer needed afterward. That is specifically about the menu flow, not about hand-editing plugin files during local development: `hooks/plugin-reload-reminder.sh` still reminds you to run `/reload-plugins` after editing `plugin.json`/`hooks.json`/`marketplace.json` under a `--plugin-dir` symlink, and that reminder is unaffected. The same release added `--json` to `claude plugin install`/`uninstall`/`update`/`enable`/`disable` (one machine-readable result line: `command`, `outcome`, `plugin`, `scope`, `message`, `failureCode`) and `errorDetails`/`noteDetails` to `claude plugin list --json` rows — `scripts/update.sh` and `scripts/uninstall.sh` now request `--json` from `claude plugin update`/`uninstall` and print the returned `message`/`failureCode` on failure, falling back to the previous generic instruction only if the CLI predates 2.1.268 or the output does not parse as JSON. It also fixed plugin/marketplace errors printing a token or password embedded in a git source URL, and hardened marketplace entry-path containment against a backslash bypass — both host-side, and this plugin's `marketplace.json` source is a plain `https://github.com/...` URL with no embedded credential, so neither was ever exposed here.

The version itself is edited in **one** place, `plugin-version.json`, then propagated with `bash scripts/check-version-truth.sh --sync`. Never hand-edit `.claude-plugin/plugin.json`'s version.

**Security note (2.1.267):** Claude Code hardened marketplace entry-path handling against a backslash bypass of its symlink/containment check (mirroring an equivalent 2.1.265 fix for plugin paths). This is a host-side fix in Claude Code's marketplace-loading code, not something `Tamircohen28/tamirs-marketplace` or this repo's manifest can trigger or needs to change — recorded here because this plugin ships *through* a marketplace listing, so the hardening is directly protective of its distribution path even though no action is required on this side.

## Skill frontmatter on Claude

Every `SKILL.md` validates against the **portable** schema, [`core/schemas/skill-frontmatter.json`](core/schemas/skill-frontmatter.json). Claude Code's own frontmatter fields are a documented **extension** of that schema — they add Claude behavior (invocation gating, tool allowlists, model hints) and are validated when present. They are not a universal requirement, and a skill is not invalid for omitting a field no other provider understands. Authoring rules: [`rules/dev/skill-quality-standards.md`](rules/dev/skill-quality-standards.md). Never hand-write a `SKILL.md` — use `skill-creator`.

Twenty-seven of this repo's `SKILL.md` files set the Claude-only `effort:` field (`low`/`medium`/`high`); no `agents/*.md` sets it. Before **Claude Code 2.1.267**, `effort:` frontmatter on a custom command, skill or subagent was silently ignored on a model with a pinned default effort — every `effort:` value shipped here could have been a no-op on such a model, with no error surfaced. The fix makes the frontmatter authoritative again; no repo-side change is needed, but it is worth knowing that these values may not have taken effect before upgrading past it. The same release added `maxEffortLevel`, an org/user-configured ceiling on `/effort` — this repo does not set one (it is a host/account setting, not a plugin default), but a user or CI environment with a low `maxEffortLevel` will silently cap a skill's `effort: high` (`deliver-dev`, `orchestrate-dev`, `plan-dev`, `pr-dev`, `start-dev`, `switch-dev`, `worker-dev`, `cleanup`, `github-policy`, `multi-agent-repo`, `repo-scaffold`, `repo-standards`, `retro`, `platform-sync`) to whatever ceiling is set, the same way `CLAUDE_CODE_SUBAGENT_MODEL_FORCE` overrides an `agents/*.md` `model:` pin (see the 2.1.257 note above) — worth knowing rather than assuming a requested effort level was honored.

### Invocation tiers (Claude-specific)

The two flags are **independent** — not a package deal:

- `user-invocable: false` — blocks the user typing `/skill-name`. Other skills, sub-agents and workflows can still call it via the `Skill` tool. This alone is what an internal companion wants.
- `disable-model-invocation: true` — blocks context-based auto-triggering **and sub-agent invocation**. It is a much heavier flag than it looks.

| Tier | `user-invocable` | `disable-model-invocation` | Examples |
|------|:---:|:---:|----------|
| User + auto-trigger (default) | `true` | `false` | plan-dev, start-dev, pr-dev, switch-dev, repo-standards, cleanup, retro |
| Explicit-only (slash, no auto) | `true` | `true` | *(none — see below)* |
| Internal companion | `false` | `false` | docs-review, mcp-pagination, changelog-review |

No skill is Explicit-only today. `switch-dev` was, and the gate cost the repo the skill's whole point: it is what an agent should reach for when a session hits a rate limit mid-objective, which is precisely when the user is not in a position to type `/switch-dev`, and the gate also made it unreachable from `orchestrate-dev`/`worker-dev` — so an orchestrated run that hit a limit could not hand off and simply died. Zero invocations across 953 sessions was the measured result.

**Gating warning:** `disable-model-invocation: true` also blocks **subagent and workflow orchestration** — a subagent invoking a skill *is* model invocation, so a gated skill cannot be fanned out across subagents. Gate only a skill that must *never* run autonomously. Prefer putting safety **inside** the skill: `cleanup` stays model-invocable with confirmation gates, a dry-run, and a script that only touches provably-safe targets; `retro` stays model-invocable because it only *proposes* changes and never writes without approval.

Internal-only skills today: `changelog-review`, `docs-review`, `mcp-pagination`. All three carry `user-invocable: false` and `disable-model-invocation: false` — hidden from the slash surface, still reachable from `repo-standards` and `mcp-builder` when those run under orchestration. `docs-review` mutates files, so it confirms before its first write when no parent skill invoked it; that confirmation is the safety, not a gate.

## Remote and headless Claude sessions

Same validation commands as the [cloud runbook in `AGENTS.md`](AGENTS.md#cloud-and-headless-runbook). Hooks in `hooks/hooks.json` apply in Claude Code sessions only; a remote session without hook support must not assume worktree hooks ran.
